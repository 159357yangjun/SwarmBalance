## 0. 结论先行 —— 四个算法现在**没有**在解同一个问题

这不影响"能不能做 V6"，但它决定 V6 的比较对象必须逐个指定。
按 BI 的指令「如发现现有算法求解的问题不一致，先报告差异，不强行比较」——以下是差异清单。

| 维度 | Greedy | PSO | GA(permutation) | OR-Tools(CP-SAT) |
|---|---|---|---|---|
| 决策变量 | 逐机队头选择（序贯贪心） | 偏好矩阵 → `argmax` 分配 | 任务排列 → 贪婪分割出**每机有序链** | `x[i][j]∈{0,1}` **仅分配** |
| 是否决定任务**顺序** | 是（隐式，先到先得） | 否（按输入序） | **是**（排列即顺序，且被局部搜索优化） | 否 |
| 目标函数 | `0.6·match + 0.4·proximity`（越大越好） | `0.6·on_time + 0.3·(−delay) + 0.1·(−energy)`（归一化后加权） | `makespan + 2·tardiness + 0.01·dist + 1e4·unassigned − 80·match`（越小越好） | `1·makespan + 1·Σ tardiness`（最小化） |
| 允许任务**不分配** | — | — | **是**（`unassigned` 有罚项 1e4） | **否**（C1 是硬等式 `==1`） |
| 电量/续航约束 | 打分里有 match 项含续航 | fitness 里累计能耗 | **硬约束**：链预估耗电 ≤ 电量×(1−0.1) | **无**（只有载重与时间窗软罚） |
| 机巢换电占用 | 仿真层处理 | 仿真层 | 解码时插入机巢往返（180 s） | **无** |
| 时间窗 | 拒因只有容量（无按时限拒单） | 计入 delay | `tardy_tolerance=600 s` 内可挂 | 进目标（软），不进可行域（硬） |

代码出处：Greedy 权重 `config/simulation.json environment.greedy` + `frontend/greedy/scheduler.py:267`；
PSO 权重 `backend_si/config.yaml:142-145`、装配 `pso_scheduler.py:690-692`（本轮实测：`weights['on_time_rate']` 在 690 行）；
GA 代价 `chain_codec.py:477-490`、调用 `ga_scheduler.py:188-195`、权重 `config.yaml:118-137`；
OR-Tools 模型 `ortools_scheduler.py:245-291`。

⇒ **最要紧的一条**：OR-Tools 目前是**分配型**模型（只求"谁做哪些任务"，不求顺序、不许弃单、不管电量），
而 GA 是**带顺序的 VRP-with-time-windows + 能量约束 + 可弃单**。
两者连可行集都不是包含关系（OR-Tools 的解可能违反电量约束；GA 的解可能违反 C1 的"全分配"）。
**直接拿 CP-SAT 的 objective 当 GA 的最优值 ⇒ 无效比较。** 详见 §5。

## 1. 三层分离（禁止用静态最优声称动态全过程最优）

| 层 | 对象 | 输入 | 输出 | 谁负责 |
|---|---|---|---|---|
| **L1 静态分配/排序问题 P_stat** | 一次批量优化 | 某时刻的 `drones_info` + `tasks_info`（快照） | 每机一条有序任务链 | `optimize()` / `_flush_buffer_with_pso` |
| **L2 动态滚动机制** | 订单到达→缓冲→触发→提交 | 事件流 | 每次 flush 产生一个 P_stat 实例 | `pending_buffer` + 三种触发（size 15 / emergency ttl 40 / timeout） |
| **L3 系统 KPI** | 仿真执行后的观测 | 逐步推进的环境 | 完成率、超时率、总里程、能耗… | `environment.step()` + `metrics_schema` |

**边界声明（论文口径必须照抄）**：
- L1 的最优性**只覆盖单次批量**，不覆盖 L2 的触发时机与批次划分；
- L2 的批次划分本身是启发式（阈值 15），它决定了 L1 实例的内容，因此**"全局最优"在 L2 层面未被定义**，不是"未证明"；
- L3 指标受 L2 与仿真执行细节（顺路接入、队头回退、机巢排队）影响，**不能反推 L1 解的质量**。
⇒ 允许的表述：*"在给定批次实例上，本算法解与独立精确基准的目标值差为 X"*。
⇒ 禁止的表述：*"本调度策略接近运营全过程最优"*。

## 2. 候选问题 P_V6 的形式化定义（供冻结，非最终）

取 **GA 实际求解的那个问题**作为基准问题（理由见 §5）。集合与参数：

- `T` 任务集，`J` 无人机集；
- 任务 `i`：取货点 `s_i`、送达点 `d_i`、重量 `w_i`、体积 `v_i`、时限 `dl_i`（可 `∞`）、优先级 `pr_i`；
- 机 `j`：速度 `sp_j`、额定载重 `cap_j`、电池容量 `B_j`、基础能耗 `e_j`(Wh/m)、载荷惩罚 `λ_j`、当前电量 `b_j`、就绪时刻 `r_j`、位置 `p_j`；
- 全局：`W_max` 多任务总重上限（30 kg）、`ρ` 电量余量（0.1）、`τ_swap`（180 s）、`tol` 超时容忍（600 s）、机巢泊位 `berths`（2）。

**决策变量**：每机一条序列 `π_j = (i_1,…,i_k)`，各序列两两不相交（并集 ⊆ `T`，允许留空 ⇒ 支持弃单）。

**硬约束**（逐条对应代码）：
| 编号 | 约束 | 代码出处 |
|---|---|---|
| H1 | 任务至多分配一次（序列互斥） | `chain_codec.py:375+ greedy_split_decode` |
| H2 | 单链累计载重 ≤ `min(cap_j, W_max)` | `environment.py:1065-1067`（生产侧同一条） |
| H3 | 链预估耗电 ≤ `b_j·(1−ρ)` | `chain_codec.py:194-195`（`_battery_use(d1)+_battery_use(d2,…)`） |
| H4 | 挂载时刻不得晚于 `dl_i + tol` | `config.yaml:135`、`try_append` 拒绝路径 |
| H5 | 机巢并发换电 ≤ `berths` | **已剔除**（阶段二实测：`backend_si/*.py` 中 `berth` 0 命中，泊位约束未进入 GA 静态优化 ⇒ 属 L3 仿真执行层，见 [`P_seq精确基准设计.md`](P_seq精确基准设计.md) §0-C1） |
| H6 | 单机链长 ≤ `max_chain_tasks = 3` | `config.yaml:117`、`chain_codec.py:159`（局部搜索同受约束 `:350`）——**§上一版漏记的一条真硬约束** |

**能耗口径**（唯一真源，两侧共用）：`E(dist, load) = e_j · dist · (1 + λ_j · load/cap_j)`，`chain_codec.py:95-99`。

**目标函数**（最小化，单位=等效秒）：
```
cost(π) = makespan(π)                       [s]
        + w_tardy · Σ_i max(0, C_i − dl_i)  [s]      w_tardy = 2.0
        + w_dist  · Σ_{j} dist(π_j)         [m]      w_dist  = 0.01
        + w_unass · |unassigned|            [个]     w_unass = 1e4
        − w_match · Σ_i match(i, π(i))      [等效秒]  w_match = 80.0
```
⚠ **单位混合是本问题的既有属性，不是我要引入的**：`s + s + m + 个 + 无量纲×80`。
`w_dist=0.01` 与 `w_unass=1e4` 实际上是在把米和"个"折算成秒。冻结时必须**原样保留这些权重**，
否则基准优化的就不是产品行为（§4 的第 3 条验收门正是这一项）。

## 4. 第二阶段设计要点（**本轮不实现**，仅备审）

- 规模：`|T| ∈ {4,6,8}` × `|J| ∈ {2,3}`，异构机型从 `config/simulation.json` 直取；
- 基准：**独立枚举**（`|T|!·…` 上界 8 任务 × 3 机 ≈ 可行的暴力空间）+ 可选 ILP/CP-SAT 二次实现；
- **不复用** `chain_cost` / `matching.compute_match`：可行性判定与目标计算各自重写一份，
  两份实现对同一批候选解必须给出**相同**的可行/不可行判定（这就是"另一实现核对"的门）；
- 记录：`cost_opt`、约束违规计数（逐条 H1–H5）、求解耗时、每个算法的 `gap`；
- **介入次数纪律**：每格必须印该算法 `optimize()` 的真实调用次数（Phase 0 的 `optimize_calls` 已有读数通道），
  `calls=0` 的格子只能记作 fallback 性能，不得记作算法性能。轻载默认配置下 PSO/GA/OR-Tools 全是 0 次 ⇒ **基准实验必须在重载工况做**（阈值 15 是工程约束，不动）。

## 5. 建议的比较对象映射（请审阅裁定）

| 算法 | 可与哪个基准比 | 理由 |
|---|---|---|
| GA(permutation) | **P_V6 精确最优**（§2） | 它真的在优化顺序 + 电量 + 弃单 |
| PSO | 只可拆成两问：① 其**分配层**能否由"分配型精确基准"评；② 顺序由输入决定 ⇒ 不参与排序质量评价 | fitness 里没有顺序自由度 |
| OR-Tools | 保持其**分配型**身份，另建一个"分配-only 精确基准"与之同题对比 | 改成链式模型会改动现有行为，违背"不修改现有调度行为" |
| Greedy | 逐机队头选择 ⇒ 只能在 L2 滚动框架内比"每次 flush 的即时解 vs 同批精确解" | 它不是一次性批量优化器 |

⇒ **需要两个基准，不是一个**：`P_assign`（分配型，服务 PSO/OR-Tools）与 `P_seq`（带顺序+能量+弃单，服务 GA）。
这是本轮最重要的发现，也是我不建议在澄清前动手写求解器的原因。
