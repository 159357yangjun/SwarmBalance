## 一、先回答"重取数据会不会让之前成果作废"

这是**四类**性质完全不同的问题，混在一起会导致要么白重跑、要么带着错误结论答辩。

| 类别 | 定义 | 重取/修正后 | 本项目实例 |
|---|---|---|---|
| **A 可追溯** | 有原始 run 记录、配置快照、seed，能重算出同样的数 | **不作废，但需重跑**。旧数字仍然真实，只是描述的是"修正前那个参数的系统" | `results/experiments/conclusion_20260911-043701/`（68 次运行，逐位可重算） |
| **B 不可追溯** | 有结果数字，但仓库里找不到产生它的运算 | **不是作废，是从来没有生效过**。必须补凭证或撤下 | `results/compare/backend_wx_metrics.csv` 六行；`paper/main.tex` 表格 |
| **C 无来源** | 参数值没有可核查出处，是设定值 | **不影响结论正确性，但"真实"这个卖点不成立**，须改措辞或补来源 | 机型参数、换电 180s、阈值 0.2 |
| **D 依赖机器** | 代码与数据都在仓库里，但**结果取决于跑它的那台机器装了什么包** | **作废风险最高且最隐蔽**：自己复跑永远是绿的，换一台机就变了 | osmnx 在否 → 碰撞体 108 vs 18 栋（见第三节） |

**D 类是本轮新识别的**，前三类都假设"同一段代码 = 同一个世界"，而加载路径分叉打破了它。
它同时把 A 类降级：结项实验虽然逐位可重算，但**换一台没装 osmnx 的机器就重算不出同样的数**，
所以 A 类的"不作废"要附加一个前提。

## 三、建筑高度覆盖率（决定"真实城市肌理"能不能说）—— 已核实，且比原记载更严重

原始 XML（`frontend/data/map/part_of_yangpu.osm`，stdlib 解析）与**真实加载器**
（`tools.osm.load_map_data`，osmnx 路径）两边我都跑了：

| 量 | 值 | 来源 |
|---|---|---|
| 建筑 way 总数（XML） | 2876 | 我亲自 iterparse |
| 带 `height` 标签 | 23（0.80%） | 同上 |
| 带 `building:levels` | 387（13.46%） | 同上 |
| 两者皆有 / 皆无 | 13 / **2479（86.20%）** | 同上 |
| 加载器返回（**本机 = osmnx 路径**） | 2889 栋；`height is None` **0**；**`height` 为 `NaN` 2864（99.13%）**；有限数值仅 **25** | `load_map_data` |
| 加载器返回（**离线 fallback 路径**） | 2876 栋；`height is None` **2479**；NaN **0**；有高度 **397** | `_load_map_data_fallback` |
| **进入碰撞集（`height > 20`）** | **osmnx 路径 18 栋（0.62%） / fallback 路径 108 栋（3.76%）** | `frontend/environment.py:161#high_buildings` 同式复算 |

### 本轮最硬的发现：**同一张地图，两条加载路径跑出的是两个世界**

`load_map_data` 按 `_osmnx_available()` 选路（`frontend/tools/osm.py:191#_osmnx_available`），
两条路径对"没有 `height` 标签的建筑"处理完全不同：

| | 有可用高度的建筑 | 碰撞体（>20 m） | 缺失哨兵 |
|---|---|---|---|
| fallback 路径 | **397** = 23 `height` + 387 `building:levels` − 13 重叠 | **108（3.76%）** | `None`（`_height_from_tags:65` `return None`） |
| osmnx 路径 | **25**（≈ 仅那 23 个 `height` 标签） | **18（0.62%）** | `NaN` |

**根因（已归因核实）**：`_height_from_tags` 会把 `building:levels × 3.0` 折算成高度
（`frontend/tools/osm.py:60-64#levels`），而 osmnx 路径**不做这个折算**，于是 387 栋有层数的楼在主流路径里全变成 `NaN`。
按 fallback 的 108 栋碰撞体逐栋归因：**94 栋**的高度是 3.0 的整数倍（= 由层数折算而来），
只有 **16 栋**带显式 `height` 标签；实测碰撞体高度取值序列 21.0 / 24.0 / 30.0 / 33.0 / 36.0 …
全是 3 的倍数。这解释了 108 → 18 的落差，也说明 **osmnx 路径下的"三维避障"几乎没有楼可绕**。

**后果（这才是关键）**：三维避障、`is_path_clear`、A\* 障碍物集合的实际规模
**取决于目标机器上 `import osmnx` 成不成功**，相差 **6 倍**（108 vs 18 栋）。
答辩机上装了 osmnx → 只绕 18 栋；评委在没有 osmnx 的机器上 clone 后跑 → 绕 108 栋。
**同一份配置、同一个 seed，航线可以不同。** 这比"高度没来源"严重一档，
因为它动摇的是"结果可复现"本身，而不是措辞。

（先前记载的 108/3.76% 是 **fallback 路径的正确值**；本轮 18/0.62% 是 **osmnx 路径的正确值**。
两个数都对，错的是"只有一个数"这个默认假设。）

**两个次级后果：**

1. **"按真实楼高渲染"不成立**，且同一座城市在三个渲染器里楼高不同：
   - Web 3D：`(bd.height||12) * VX`（`console/static/index.html:2300#bd.height`）

   - `12` 米与 `层高×3.0`（`frontend/tools/osm.py:63#3.0`）**均无来源**
   即 osmnx 路径下 **99.13% 的建筑在 3D 视图里是同一个编造高度 12 m 的盒子**。
2. ~~`environment.py:282` 打印 `加载了 {len(high_buildings)} 个具有高度信息的建筑物`~~

### 新发现（本轮）：两条加载路径的"缺高度"哨兵不一致

- **osmnx 路径**：缺失高度给成 **`NaN`**（实测 2864 个）。
- **离线 fallback 路径**：`_height_from_tags` 明确 **`return None`**（`frontend/tools/osm.py:66#return`）。

当前两个消费方恰好都安全：`frontend/environment.py:161#is not None` 的 `is not None and > 20` 让 NaN 落到 `False`；
`console/sim_session.py:710-711#isfinite` 有 `if not math.isfinite(h) or h <= 0: h = 12.0` **已经挡住 NaN**
（所以 **不存在** NaN 被 `json.dumps` 写成非法 `NaN` 打崩前端 `JSON.parse` 的问题——我专门查过）。
但任何新代码写 `if b["height"] is not None: 用它算`，就会**静默拿 NaN 做算术**。
→ 属于 P1：在 `load_map_data` 出口把两条路径统一成同一种哨兵，成本一行。

### 核对通过（避免误伤，这些不要改）

- **无任何 ZeroDivisionError 可达**，无 NaN/inf 出口。
- **`total_energy_consumed` 是可信的真实放电量**：实测 `初始14637.60 + 补入5412.14 − 期末8114.47 = 11935.27` 与字段值 **差 0.00 Wh**；`current_battery` 钳位整局 0 次触发。
- `空载里程 + 载货里程 == 总里程`（残差 −0.0000 m）。
- `timeout_rate == 1 − on_time_rate`；`优先级三档 totals 求和 == total_delay`；`周转率 × 泊位数 == 换电次数`（20/20 行精确）。
- **完成率饱和不是 bug**：68 行里 65 行 = 1.0、stdev 0.000000。这说明**实验从未跑到有区分度的工况**，而非公式错。副作用：M1 的分母偏差在这批数据里恰好为 0，所以"数据看着自洽"掩盖了机制。
- 聚合层无问题：`_mean_rows` 拒绝静默补零、`样本数`/`配对样本数` 有导出、配对 seed 真的一一对应（四算法均为 {101..105}，无重复）。

- **M4「空载率口径换了东西」—— 已证伪，代码不要动。** 我一度按 `current_load > 0`
  去核对，得出"98.53% 的『空载』里程其实带货"，**这个结论是错的，我撤回**。

## 七点五、同配置同 Seed 的运行确定性（2026-09-29 实测，不是推断）
