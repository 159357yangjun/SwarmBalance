# 无人机设备数据：来源登记与能耗标定方案

> 本文件是 `docs/数据溯源与统计分析.md` §1「数据来源分级」的**执行层**：那份文档说清"哪些是真数据"，
> 这份说清"缺的那些该去哪儿拿、拿到后怎么算、算出来的东西能撑到什么程度的结论"。
>
> **一句话定性**：本项目当前**没有任何实机飞行数据**。设备参数只有 ① OSM 真实底图 与
> ② FlyCart 30 电池容量（2×1984.4 Wh，逐位吻合官方）属于外部可核；其余为厂商铭牌对标或无来源设定值。
> 因此 Validation（模型是否代表真实系统）不成立，只能做 Verification + Sensitivity。

## 1. 本轮最硬的发现：能耗量级错了，不是"偏一点"

从仓内一手运行记录现算（`raw_runs.csv`，algorithm_comparison 20 行）：

| 算法 | Wh/km（mean±sd） | 区间 |
|---|---|---|
| greedy | 0.083 ± 0.002 | [0.080, 0.086] |
| ga | 0.084 ± 0.003 | [0.080, 0.088] |
| ortools | 0.084 ± 0.003 | [0.080, 0.088] |
| pso | 0.084 ± 0.003 | [0.080, 0.089] |

复算命令（项目根目录，可直接复制）：

```bash
PYTHONIOENCODING=utf-8 ../.venv310/Scripts/python.exe -c "import csv,pathlib,statistics as st;rows=[r for r in csv.DictReader(open('results/experiments/conclusion_20260911-043701/raw_runs.csv',encoding='utf-8-sig')) if r['实验']=='algorithm_comparison'];print({a:round(st.mean([float(r['总能量消耗'])/float(r['总飞行距离']) for r in rows if r['算法key']==a]),4) for a in ('greedy','ga','ortools','pso')})"
```

对照外部锚点：DJI FlyCart 30 官方 = 双电 3968.8 Wh ÷ 满载航程 16 km ≈ **248 Wh/km**。

⇒ **当前仿真比真实世界低约 3000 倍。** 后果链条很具体：耗电几乎不吃电量 ⇒ 仿真里几乎不必回巢换电 ⇒
机巢永不拥堵 ⇒ 完成率顶到 1.0。也就是说**"四算法完成率全为 1.0"这个饱和现象，很可能是这个量级错误造成的，
而不是四种算法真的都能做完全部任务**。这条必须在重标定后重新判定。

## 4. 能耗模型：不要一条"每分钟掉固定百分比"

现在的实现是单一 `battery_consumption_base` + `battery_load_penalty_factor`，把起降、巡航、爬升、悬停全压成一个常数。
改成**分段功率模型**，每段一个系数，且每个系数都要有"来源"栏：

```
P_total = P_hover(m) + P_cruise(v, m) + P_climb(h_rate, m) + P_payload_dropoff
E_flight = ∫ P dt        ← 与 CMU 数据的口径一致（电流×电压对时间积分），因此可直接对撞
```

标定流程（拿到 E1 的 CSV 之后）：

1. **按整次飞行划分**（不是按帧随机划分）：留出若干次飞行完全不参与拟合 ⇒ 防止同一次飞行的相邻帧同时进训练与测试。
2. 用 0 / 250 / 500 g 三档载荷做**载重-功率回归**，检验斜率是否显著（n=209 足够出置信区间）。
3. 报告**总耗能误差**与**飞行时间误差**两个指标，分别给 MAPE 与留出集结果。
4. 只有多旋翼能用这条曲线；若将来引入固定翼 / 垂直起降固定翼，**必须分开建模，不得共用**。
5. 无实测的机型（ARK40、美团）用「厂商电池 Wh ÷ 满载航程 km」派生初值，并在表里标 **估算模型**，
   例如 FlyCart 30：3968.8/16 ≈ 248 Wh/km —— 这个数本身可作为多旋翼量级的 sanity check。

长期衰减（SOH）与单次耗能是两件事：前者需要**电池编号 + 循环记录 + 容量/健康状态**，
E1/E2 这类短期飞行日志通常回答不了 ⇒ 调度仿真里先不建 SOH，除非拿到 E4。

## 6. 第一版推进顺序（零硬件可启动）

1. **收窄场景**：选一个小区域 + 一种业务（如园区配送），明确评估目标是完成率 / 耗能 / 延误 / 换电次数中的哪几个。
2. **单机型建能耗模型**：只用有公开实测支撑的那一款（M100 via E1）建并验证能耗模型，按 §4 的留出集检验。
3. **扩虚拟机型**：用厂商参数限制载重/速度/可用能量，逐个标注「有实测支持」或「估算模型」。
4. **真实地图上跑多机调度**：含任务插入、返航、充电排队；初期可用简化飞行模型，先把调度逻辑跑对。
5. **补测代表性工况**：借机/租机/合作方，优先补**载重变化、不同速度、不同电池状态**三类，不必一次覆盖全组合。
6. （可选）若要验证飞控指令与多机交互：PX4 + Gazebo 多机仿真——但其输出**仍需实测校准**，不能当 Validation。

## 7. 每项数据必须记的五元组

这是这份文档的核心要求，也是后续所有入库数据的模板：

| 字段 | 含义 | 反例（本项目现状） |
|---|---|---|
| 来源 | URL/文件名/机构 + 获取日期 | README 曾写"取自公开产品规格"但外链 0 条指向规格页 |
| 机型 | 具体型号与代次 | `standard_cargo` 标 ARK40，但 speed 无任何来源标注 |
| 测试条件 | 无风/海平面/温度/载荷档位 | 官方 16 km 是"满载+无风"，项目直接当可用航程，未存条件 |
| 实测 or 估算 | 二选一，不许含糊 | `battery_consumption_base` 三个值均属"含糊"，实为无来源设定 |
| 误差范围 | 给出区间或置信度 | 全部参数目前无误差范围 |
