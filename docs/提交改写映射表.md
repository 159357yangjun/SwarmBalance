# 提交改写映射表（旧 sha → 现 sha，含复算式）

这份表存在的唯一理由：本仓 2026-09-30 做过**两轮 message 改写**（只改提交信息、不动树），
指针全变了。改写后旧 sha **从 HEAD 不可达**，任何人（含别的会话、以及外部台账）引用的旧 sha
都可能落到"对象还在但悬着"的状态 —— 那张映射表只有仓这边能出，所以进仓。

- 每行都带**复算式**：`git log --grep='<标题片段>'` 一类的命令。标题不受改写影响，
  所以 **sha 只当辅助，标题/复算式才是主键**（这条是台账侧定的规矩，这里照做）。
- 这份文件里**不写任何"当前值"**（`ahead` 有几笔、`diff --stat` 多少行都会随 HEAD 移动）：
  要现值就跑下面第二节里的命令，别信这里曾经印过的数。下面出现的 `42` 是唯一不漂移的那一对，
  因为它是"改写边界两侧"的对照，之后再加提交也不变。
- **旧对象会不会消失：会。** 旧 sha 现在只靠 reflog 活着（`git reflog` 里当时可见
  `370b9fc`/`6f83007`/`4520523`）。`git gc` 按 `gc.reflogExpire`（默认约 90 天）回收后，
  这些对象就没了，届时 `git cat-file -t <旧sha>` 会报 `Not a valid object name`。
  ⇒ 长期引用请用复算式，不要用旧 sha。

## 二、复算式（把 sha 当输入而不是结论）

```bash
# 1) 按标题找当前活着的提交（改写只动 message 尾部一行，标题没变，所以这条稳）
git log --format="%h %s" | grep "给\"作废\"补上量"
git log --format="%h %s" | grep "缺依赖的第一条应用命令不再抛满屏栈"
git log --format="%h %s" | grep "一条\"总是 skip 的门\""
git log --format="%h %s" | grep "纪律分两半"

# 2) 证"只改 message、没动树"：同一位置的新旧两端 diff 为空（rc=0）
git diff --quiet 4520523 873f069; echo rc=$?     # 0 = 树未变
git diff --quiet 370b9fc ab830e7; echo rc=$?
git diff --quiet 2550328 4adc947; echo rc=$?
git diff --quiet 2294adc b9d37c7; echo rc=$?

# 3) 证"没丢提交、也没多提交"：改写边界两侧计数必须相同（这两端是固定的旧 sha，不漂移）
git rev-list --count origin/master..370b9fc      # 改写前的链尾
git rev-list --count origin/master..ab830e7      # 改写后的链尾 —— 两条数字必须相等
git rev-list --count origin/master..HEAD         # 只随新工作增长，与改写无关，别拿它当判据

# 4) 旧 sha 现在的真实状态（"还在"不等于"可达"，两个都要测）
git cat-file -t 4520523                          # commit（对象仍在）
git merge-base --is-ancestor 4520523 HEAD; echo rc=$?   # rc=1 = 已从 HEAD 不可达
```

注意 2) 里**不能**写成 `git diff <旧sha> HEAD`：那之间已经有了真实新工作，
差值必然非空、而且每加一笔就再变一次 —— 它证明不了任何东西。
"树未变"只能在**同一位置的新旧两端**之间断言（就是 2) 那四条）。


⇒ 所以这张表在那一件落地后**必须整张重生成**（第一节所有"现 sha"都会再变一次）。
