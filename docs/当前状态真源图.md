## 2. 实测到的逻辑矛盾（本轮最重要发现）

同一次回合（seed=40907，1200 步跑满，`done=True`）：

```
记录到 _record_task_completion 调用 27 次
  ├─ 送达路径 (dest)      15 次   ← 无人机确实抵达 destination
  └─ 兜底路径 (fallback)  12 次   ← is_free 转换时清理剩余 assignment
兜底事件里 load_time is None（从未取货）= 5 / 12
log 中 delivery_time == 0 的行数        = 12   ← ⚠ 与上一行不同：见 §2-bis 的口径说明
env.total_completed_tasks               = 27   ← 全部计入"完成"
```

⇒ **12 个未经"抵达 destination"判定的任务被计入 `total_completed_tasks`，其中 5 个连货都没取。**
这是 BI 定义的那种真不自洽：不是预测误差，而是**执行结果与业务语义不一致**——任务没被送达，却记为完成。

机制解释（代码级）：`_record_task_completion` 对两种情况用同一套算法，
`delivery_time = max(0, completion_time − load_time)`，而 `load_time is None` 时被兜底成 `assigned_time`
（源码可见 `if load_time is None: load_time = assigned_time`）⇒ 未取货的任务得到一个"看起来正常"的
`delivery_time`，而不是"未完成"标记。

⚠ **两个数的口径差别（我自己差点在这里写错）**：
`load_time is None` 只有 **5** 个（真·从未取货），而 `delivery_time == 0` 有 **12** 个 ——
后者包含"取了货但取送同刻"的情形。所以**不能把 12 说成"12 个从未取货"**；
能站住的表述是：**12 个走兜底路径、未经送达判定即计为完成，其中 5 个明确从未取货**。

**为什么以前没人发现**：`Task.status` 从不写终态（所以前端/API 看不到矛盾）、
统计只加计数器（所以聚合值看着正常）、且 `completed_task_log` 只留最近 120 行（长回合里连明细都会被截掉）。

### 2-bis 这条发现的边界（不外推）
- 样本 = **1 个 seed × 1 种驱动方式（贪心直派）** ⇒ 12/27 = 44% 是这一格读数，**不是全局率**；
- 我的驱动是自己写的循环（把 pending 顺序塞给空闲机），**与生产 `greedy_action_from_observation` 不完全同源** ⇒
  兜底触发频率可能被我放大。**必须用生产 worker 复算后才能引用这个百分比**（下一步第一件事）。
- 但"**兜底路径会把未取货任务计为完成**"这一条是**代码级事实**，与驱动方式无关，足以立门。

## 6. 生产路径复现（BI 第 1 步，本轮完成）与三套数据定性

### 6-A `completed_task_log` 也不是"完成真源"（采纳 BI 第三处纠正）

本轮实测确认它是**有上限的审计记录**而非真源 ⇒ 当前系统实际是**三套性质不同的数据**，没有一套是完整、持久、逐任务的 completion truth source：

| 数据 | 性质 | 证据 |
|---|---|---|
| `completed_tasks` | **单步临时缓冲** | `environment.py:239-242` 注释 + `:1528` 每步 `clear()` |
| `completed_task_log` | **有上限的审计记录（会截断历史）** | `:480-481` `if len(...)>120: del [:-120]` |
| `total_completed_tasks` | **真正承重的聚合计数器** | `:276` 定义、`:465` 附近自增；统计只读它 |

⇒ C1 的问题因此更清楚：**唯一承重的是一棵计数器，而它没有任何可核对的明细层。**

——即论文实验用的同一条正式路径，含 `greedy_action_from_observation`。

```
  ├─ dest（抵达 destination）  26

  task_3   t=172  load=None  assigned=0
  task_8   t=190  load=None  assigned=0
  task_24  t=886  load=None  assigned=446
```

⇒ **BI 要求的最小判据达成**：至少存在一条 `completion_reason=is_free_cleanup` 且无 delivery evidence 的任务

### 6-D cleanup × timeout/delay 交叉污染核查（BI 要求补掉的一格，本轮完成）

**真实计算入口与分母**（不反推，直接读源码定位）：

| 指标 | 入口 | 分母 |
|---|---|---|
| `timeout_rate` | `environment.py:986` = `1 − total_on_time_tasks / total_completed_tasks` | **被污染的计数器本身** |
| `on_time_rate` | `:985` = `total_on_time_tasks / total_completed_tasks` | 同上 |
| `avg_delay` | `:987` = `total_delay / total_completed_tasks` | 同上 |
| `delay` 单条 | `:439-443` = `max(0, completion_time − deadline)`，`deadline is None ⇒ 0` | — |
| `is_on_time` | `:445` `delay <= 0` → `:463 total_on_time_tasks += 1` | — |

⇒ **三个 KPI 共用同一棵被污染的分母**，所以只要 cleanup 进了计数，完成率、超时率、平均时延同时受影响，不是只污染分子。

**实测（seed=40907 / greedy / 1200，生产 worker）**——归因用"每次调用前后计数器增量"，非事后猜测：

```
恒等式核对（证明归因可信）：ΣΔcompleted=38 == KPI完成任务数=38.0
                            ΣΔon_time=36  → 超时数=2，与发布超时率 0.0526×38=2 一致
                            ΣΔdelay=106.5 == 平均时延 2.8026 × 38 = 106.5

cleanup_completed            = 12    in_timeout = 1   in_delay = 1   Σdelay = 85.5
never_loaded_cleanup         =  3    in_timeout = 0   in_delay = 0   Σdelay =  0.0
dest（对照）                 = 26    in_timeout = 1   in_delay = 1   Σdelay = 21.0
```

⇒ **答案是 >0，不是 0**：按 BI 给的分支，`timeout_rate` 与 `mean_delay` **确实受同一个生命周期错误直接污染**。
且 cleanup 那 12 条贡献了全部延迟量的 **80.3%**（85.5 / 106.5），而只占完成数的 31.6% ⇒
**它对平均时延的污染强度远大于对完成率的污染强度**。

**反事实重算（剔除 12 条 cleanup，分母各自取真值）**：

| 指标 | 发布值 | 剔除后 | 差值 |
|---|---|---|---|
| 完成率 | 0.8636 | 0.5909 | **+0.2727** |
| 超时率 | 0.0526 | 0.0385 | **−0.0142** |
| 平均时延 | 2.8026 | 0.8077 | **−1.9949** |

⚠ 这是**影响量级估计，不是修正值**：它假设"剔除即正确"，而 cleanup 应归入哪个终态尚未定（§6-F）。
n=1 seed ⇒ 数值不外推；结构事实（三 KPI 共用被污染分母）才外推。

**一处必须点名的自我纠错**：我第一次算反事实时把超时数写成 `int(round(超时率×T))` 再套错符号，
得到"剔除后超时率 **1.3462**"这种 >1 的非法值 —— 是坏算式而非新发现。修成"逐条 `d_ontime` 求和"后才得 0.0385。
教训：**派生比率算完必须验定义域**（概率类越界即算式坏，先怀疑量具）。

**never_loaded 的 delay=0 是巧合，不是免疫**（这条差点被我写成结论）：三条的 `cleanup_t`（172/190/886）
都小于各自 `deadline`（626/579/1071），而 `delay` 只看 `completion_time − deadline`、**与是否取货无关** ⇒
换一个 deadline 更紧的实例，未取货任务同样会计入超时。故不得写"未取货任务不影响时延"。
