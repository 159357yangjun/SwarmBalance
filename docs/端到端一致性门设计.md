# 端到端逻辑一致性门（E2E Consistency Gate）设计

> 三层可信度结构里的第二层：**V6 证"数学问题解对没有"，本门证"仿真故事自相矛盾没有"，外部 Validation 证"这故事多大程度符合现实"。**
> 状态：**设计稿 + 现状实测**。本轮先测"哪些不变量今天有证人、哪些根本没有"，未写门代码。
> ⚠ 本文不声称系统已具备这些能力 —— §2 的结论是**四条今天无法直接建门**，需要补可观测状态。

---

## 1. 核心判据（BI 提出的那一条）

> **前一层做出的假设，不能被后一层无声地推翻。**

"预测有误差"本身不是不自洽（现实也如此）。不自洽的是三件事之一：
① 预测值与执行值**没有被区分记录**；② 执行失败**没有反馈通道**；③ 下一次决策**不使用新状态**。

⇒ 由此得到本门的总设计原则：**先让每一层的假设变成可读取的状态字段，再谈验证它。**
没有留痕的假设，门既不能证明成立也不能证明违反 —— 那种门是空转的。

## 2. 现状实测：五条不变量各自的"证人"在不在

| 不变量 | 定义 | 本轮实测 | 能否今天建门 |

| **I5 统计一致** | 完成数可从任务状态+事件独立重算 | 统计走 `completed_tasks` 列表（`:239,479`），**不从 Task.status 推**（`status=='completed'` 在 environment.py 命中 0）⇒ "独立重算"目前只是换一种写法读同一个列表，不构成第二证人 | ❌ **不能**（同 I1 根因） |

按项目自己的规矩：期望值为 0 的夹具给不了护栏牙 —— 我不会为这三条写"看起来像门"的断言。

## 3. 关于你最关注的「调度 vs 机巢」：两个问题分开，且你的例子在执行层是成立的

实测支持 BI 的两段论：

- **执行层自洽性：成立。** 泊位容量真在管（`has_berth`/`occupy`/`vacate`），满了会进 `_nest_waiting` 队列，由 `_manage_berths` 按紧迫度动态仲裁移交 ⇒ B 确实等待，时间与电量随之更新。
- **调度层合理性：不成立（缺口真实存在）。** `backend_si/*.py` 中 `berth` **0 命中** ⇒ GA 的静态优化完全看不到泊位竞争。

⇒ 准确表述是 BI 给的那句：**GA 正确解决了一个简化问题，而该简化问题没覆盖执行系统的全部重要约束。**
这不是实现 bug，也不是"GA 算错了"，而是**建模间隙（modeling gap）**。

因此 V6 报告里必须把两类差距分开写：
```
算法间隙 (algorithmic gap)  = c_GA − c_opt(P_seq)      ← Oracle 能答
建模间隙 (modeling gap)     = cost(P_seq 最优) 在真实执行下的表现 − 系统层面可达的表现   ← Oracle 答不了，只能由 E2E 门 + 实验 C 观测
```
⚠ 建模间隙今天**无法量化成单一数字**（"系统层面可达"没有参照物），所以本阶段只做定性声明 + 用 I4 门保证执行层不越界。
把它写成"gap = X%"会是新的越界。

## 4. 需要先补的最小可观测面（**不改行为，只加留痕**）

这是本门真正的前置工作，比写断言更重要：

| 编号 | 补什么 | 为什么必须有它才能建对应的门 | 是否改变行为 |
|---|---|---|---|
| P-1 | 任务终态落库：完成/失败时调 `update_status('completed'/'failed')` | I1、I5（否则第二证人无从独立产生） | **可能改**（若下游读 status）⇒ 必须先做消费链普查 |
| P-2 | 事件日志：`{task_id, drone_id, kind ∈ {created,assigned,pickup,delivery,swap_start,swap_end,queue_join,queue_leave,fail}, sim_time}` | I2 跨步核对、I3 顺序校验 | 否（纯追加） |
| P-3 | 预测留痕：分配时记下 `predicted_energy_wh / predicted_eta_s`，执行完记 `actual_*` | I3 与 §1 的核心判据 | 否（纯记录） |
| P-4 | 电量写入归因：四处写入各带一个 reason 标签 | I2 | 否 |

P-3 是关键一条：**有了它，"调度器认为要 100 Wh、实际耗 150 Wh"才从一句担忧变成一个可统计的量**
（预测误差分布），也正是论文第三层（现实有效性）将来要用的同一套数据结构。

⚠ **P-1 的消费链普查本轮已跑，结论与我的预期相反**：全仓扫 `\.status\b`（排除 `self.status` 定义处），
命中 **3 处且全部是同名不同物** —— `console/server.py:821` 是实验服务状态、
`console/zip_range_extract.py:38-39` 是 HTTP 响应状态；**`Task.status` 的读取方 = 0**。
⇒ P-1 补终态赋值**不会改变现有行为**（没有下游读它），但代价是另一面：
**`Task.status` 今天是一个纯装饰字段**（写了没人读、且从不写终态），属于本项目已登记过的"死字段"族
（见 `console/test_dead_charging_fields.py` 的 writers/readers 口径）。
所以 P-1 的真实成本不是回归风险，而是"要让 I1/I5 有第二证人，得先把这个字段接进统计路径"——
即 EG-4 要求完成数从事件日志重算而**不读** `completed_tasks`，两者才形成互证。
凡"看起来只是补个赋值"仍属改动产品代码，**要你点名**才做；我不自行开工。

## 7. 与三层结构的对接

| 层 | 载体 | 回答的问题 | 证据类型 |
|---|---|---|---|
| 数学 | V6 Oracle（A/B 实验） | 算法有没有解对**它自己定义的那个问题** | 最优性差距 Δ、违规计数 |
| 系统 | **本门** + 实验 C | 这个问题产生的决策在仿真里有没有自相矛盾、运营表现如何 | 不变量通过 + 配对 KPI |
| 现实 | 外部 Validation（Validation Matrix） | 这个自洽的故事多大程度符合真实飞行 | 预测误差、适用范围 |

**逻辑自洽 ≠ 现实真实**（BI 明示）：一个"匀速、无通信延迟、电池严格线性"的世界可以完全自洽而不真实。
⇒ 论文措辞分三档，不得互相顶替：**内部逻辑自洽性 / 算法正确性 / 现实有效性**。
