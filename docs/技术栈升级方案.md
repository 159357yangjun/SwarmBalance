# 技术栈升级方案（Python / osmnx / numpy）

> 本文档是「群智优衡 SwarmBalance」的依赖升级迁移清单。
> 目标：把项目从被过时版本锁死的状态，迁移到更现代、更易协作的技术栈。
> 状态：**方案待执行**（需在可运行验证时按步骤推进，当前仅静态分析）。

---

## 一、为什么升级（结论先行）

项目当前的依赖栈存在一个历史遗留的「锁死链」：

```
osmnx==1.9.4（旧版，Requires-Python <3.13）
   └─ 逼着 Python 降到 3.10
   └─ 逼着 numpy 钉死在 1.26.4（因为 osmnx 1.9.4 要求 numpy<1.27）
        └─ 逼出"必须先 pip install numpy==1.26.4 再装其余"的诡异安装顺序
             └─ 逼出"pip 必须降到 23.x 绕开 safe-delete bug"
```

这套约束**在 2026 年已经全部过时**：

| 依赖 | 现状 | 目标 | 依据 |
|---|---|---|---|
| Python | 3.10（2021 发布，**2026-10 EOL**） | **3.12** | osmnx 2.x 支持 3.11~3.14 |
| osmnx | 1.9.4（2024-07） | **2.x**（最新 2.1.1） | 2.0 于 2024-11 发布，API 稳定 |
| numpy | 1.26.4 | **2.x** | osmnx 2.x 要求 `numpy>=1.22`，与 ortools 不再冲突 |
| pip | 需手动降到 23.x | 系统默认即可 | pip 26 的 safe-delete bug 与旧依赖链绑定，升级后无此问题 |

**结论：架构不需要重做。** Python 是无人机调度与算法科研的标准生态（shapely / ortools / pymarl / geopandas 全是 Python），换语言得不偿失。问题只在依赖版本，升级即可解除。

## 二、项目用到的 osmnx API 及 2.x 影响

`simulation/tools/osm.py` 是 osmnx 的**唯一入口**（environment 只用建筑、可视化才用路网），影响面可控：

| 调用 | 2.x 是否保留 | 注意点 |
|---|---|---|
| `ox.graph_from_xml(path)` | ✅ 保留 | 可选参数改为 keyword-only，位置参数调用不变 |
| `ox.project_graph(graph)` | ✅ 保留 | — |
| `ox.features_from_xml(path, tags={...})` | ✅ 保留 | 1.8 已从 `geometries_from_xml` 改名而来，项目已用新名 |
| `ox.project_gdf(gdf)` | ✅ 保留 | — |
| `graph.graph['crs']` | ⚠️ 需验证 | 属性字典机制未变，但建议改为更稳妥的取值方式 |
| `buildings.to_crs(crs)` | ✅（geopandas） | 与 osmnx 无关 |

**唯一需要重点验证的是 `graph.graph['crs']` 的取值**——若 2.x 改变了该属性的存放方式，会导致建筑投影失败。备选写法：直接用 `ox.project_gdf(buildings)`（自动投影到 UTM），不再依赖 `graph.graph['crs']`。

## 三、分步迁移步骤

### 第 1 步：新建 Python 3.12 虚拟环境

```bash
# 确认本机有 3.12（py -0 查看已装版本；没有则从 python.org 装 3.12.x）
py -3.12 -m venv .venv312
.venv312\Scripts\activate          # Windows
# source .venv312/bin/activate      # macOS / Linux
```

### 第 2 步：先装新版 requirements（不再需要"先钉 numpy"的诡异顺序）

把 `requirements.txt` 顶部的 numpy 行改掉，然后**正常顺序一次性安装**：

```txt
# 2.x 不再要求 numpy<1.27，numpy 2.x 与 ortools 也不再冲突
numpy>=2.0,<3.0

osmnx>=2.0,<3.0
shapely>=2.0
geopandas>=1.0
fiona>=1.10
pyproj>=3.7
networkx>=3.3
pandas>=2.2
requests>=2.32

pygame>=2.6
matplotlib>=3.9
PyYAML>=6.0

ortools>=9.14
protobuf>=6.0

fastapi>=0.115
uvicorn>=0.30
pydantic>=2.6
```

```bash
pip install -r requirements.txt
```

> 若需要精确复现，装完后 `pip freeze > requirements.lock.txt` 生成锁文件。

### 第 3 步：验证 osmnx 2.x 下地图加载

这是**最关键的一步**，跑一个最小脚本确认建筑加载与投影没坏：

```bash
cd frontend
python -c "from tools.osm import load_buildings, load_map_data; b = load_buildings('data/map/part_of_yangpu.osm'); print('建筑数:', len(b), '示例坐标:', b[0]['geometry'].centroid if b else None)"
```

预期：建筑数约 110，坐标是米制（如 358000 / 3460000 量级），不是经纬度（121.x / 31.x）。

### 第 4 步：回归跑一次完整评测

```bash
cd frontend
python evaluate_metrics.py --policy greedy --episodes 1 --episode-steps 600 --seed 100
```

对照迁移前的指标（完成率约 0.72、禁飞绕飞>0），若建筑投影正确、禁飞区/任务链照常生效，即迁移成功。

### 第 5 步：清理旧环境与旧依赖

```bash
# 确认 .venv312 跑通后，删除旧 .venv310 与项目外备份
# （旧 .git 备份 .git_backup_drone_* 若已无用也一并清理）
```

## 四、迁移后的收益

1. **安装体验**：队友 clone 后 `pip install -r requirements.txt` 一条命令装完，不再需要"先钉 numpy、降级 pip"的玄学操作；
2. **性能**：osmnx 2.x 对 features 模块做了重构优化，建筑解析更快；
3. **可维护性**：Python 3.12 有更长的支持周期，numpy 2.x 是当前主线，不再被下游包嫌弃；
4. **协作友好**：新人不会卡在"我 Python 3.13 装不上项目"这种环境问题上。

---

## 五、备选方案（若 osmnx 2.x 迁移受阻）

项目对 osmnx 的依赖其实**很浅**——只要"解析 OSM 文件 → 提建筑轮廓+高度 → 投影到 UTM"。若 2.x 迁移遇到无法解决的 API 问题，可考虑更轻的替代：

| 方案 | 优点 | 缺点 |
|---|---|---|
| **pyrosm** | C 加速解析 OSM，速度最快 | 主要支持 PBF 格式，`.osm` XML 支持有限 |
| **pyosmium** | 流式解析，内存友好 | 需手动拼 shapely 几何 + pyproj 投影，工作量中等 |
| **直接 XML 解析**（xml.etree/lxml） | 零重依赖 | 只适合"只要建筑"的场景，路网要自己写 |

> 建议：优先走 osmnx 2.x 迁移（改动最小）；只有当 2.x 迁移卡住时，再评估 pyosmium 方案。

## 六、回滚方案

迁移前先把当前能跑的版本打一个 tag（或保留 `.venv310` 不动）：

```bash
git tag v0.1.0-legacy-py310   # 迁移前打标（稳定版阶段再提交）
```

若迁移后跑不通，回滚只需：

```bash
git checkout v0.1.0-legacy-py310
# 或重新用 .venv310 跑（旧环境不删即可随时切回）
```
