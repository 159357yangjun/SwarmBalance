## 1. 仿真系统三个不同的可信度问题

| 层次 | 核心问题 | 典型证据 | 不允许推出 |
| --- | --- | --- | --- |
| **V：软件验证（Verification）** | 代码是否正确实现**已经明确定义**的仿真规则？ | 状态机、断言、守恒账本、边界反例、精确 SHA CI | 代码通过测试 ⇒ 飞行物理真实 |
| **M：概念/运行模型确认（Validation）** | 规则与参数对指定问题和工况是否足够贴近现实？ | 数据来源、独立实测、误差、失效工况、敏感性与不确定性 | 模型适用一种机型 ⇒ 可外推到另一机型 |
| **E：实验/结论可信度** | 给定模型用途，算法比较是否公平、可复现且结论不过度扩展？ | 固定外生输入、配对实验、算法确实被调用、执行结果及统计区间 | 内部适应度最高 ⇒ 现实配送最优 |

以上是项目使用的**实用三层框架**，不是直接逐字摘引 NASA 标准。NASA-STD-7009B 与其配套手册强调模型用途、验证/确认、风险与可信度评估；ODD 强调在代码之外明确模型实体与过程规则（来源见附录）。

## 2. 九个逻辑自洽维度

| 维度 | 项目中需要明确的契约 | 典型反例 |
| --- | --- | --- |
| 1. 用途、边界、抽象层次 | 研究配送调度与运营级运动学；列明**未**模拟飞控/感知/真实三维动力学 | 用 3D 可视化宣称 3D 物理真实 |
| 2. 时间与因果 | `step_seconds`、事件同刻排序、生成/分配/取货/送达/故障发生次序 | 同时刻先结算后取货；跨重放次序漂移 |
| 3. 状态机与身份 | Task/Drone/Station/货物有互斥状态及唯一身份；禁止无证据状态跃迁 | 订单统计已完成但 `Task.status` 仍是 `assigned` |
| 4. 资源与账本 | 订单唯一性、货物保管、机载载重、电池扣减、换电、泊位容量 | 货物凭空消失；空电仍飞；同一机占两个泊位 |
| 5. 地理和运动 | 投影单位 m；路径规划与实际位移同场景障碍；运动是明确的模型简化 | 调度预计直达但航线绕障，二者未分离记录 |
| 6. 参数与量纲 | s、m、m/s、kg、Wh、Wh/m、Wh/km 标注；默认与开关透明 | m 当 km，`assigned` 与 `onboard` 计费混用 |
| 7. 决策与执行 | 调度器只提出建议；环境负责合法性判定、拒绝理由和真正执行 | 调度预测成功，实际不合法却被记为完成 |
| 8. 观测与指标 | 所有 KPI 定义清晰、可从独立执行事件重算；正确处理未完成与截尾订单 | 仅报告已完成订单超时率，隐去积压 |
| 9. 复现、覆盖和可信边界 | 固定世界输入、精确源码版本、检测器有正/负例、报告未测情形 | 相同 seed 却共享随机流导致订单序列不同 |

**重要：内部一致不等于真实。** 一个“匀速、无通信延迟、线性能耗”的世界可以内部自洽，但对真实无人机适用范围有限。

## 3. 建议的“世界”概念模型

### 3.1 实体、身份和所有权

- **Order**：订单 ID、取送货位置、重量、SLA、优先级、生成时间、所属无人机/交接方、生命周期、真实送达凭证。
- **Cargo/Manifest**：订单对应货物唯一身份、当前保管方、数量/重量；取货、故障与合法交接均是**事件**，而不是自行覆盖一个重量字段。
- **Drone**：机型、米制位置、`current_battery_wh`、`assigned_load_kg`（承诺容量）及 `onboard_load_kg`（真实机载）；航线和服务状态；两种载重语义不得混淆。
- **Station**：状态、泊位总数、占用集合、等待队列、换电会话。
- **Environment/WorldState**：唯一世界时钟、任务注册表、机队、机巢、路径/障碍、随机流、执行事件账本。
- **Scheduler**：从**观察快照**计算候选动作；预测值属于“预测”，不可冒充执行事实。
- **Renderer/Console**：只读世界快照；交互命令通过受控服务接口影响下一状态，不允许反向用界面图形改变模拟物理。

### 3.2 事件及任务生命周期

建议最终定义一个具有证据的业务事件词汇：
`TASK_CREATED` → `TASK_ASSIGNED` → `PICKUP_COMPLETED` → `DELIVERY_COMPLETED`；另有 `TASK_CANCELLED`、`TASK_FAILED`、`TASK_REQUEUED`、`DRONE_FAILED`、`CARGO_HANDOFF`、`SWAP_STARTED`、`SWAP_FINISHED`。

- 正常订单不得在取货之前计入送达。
- “无人机空闲”仅是无人机状态，**不是**订单送达证据。
- 错误、取消、故障恢复/回收要有独立事件类型；“终态”与“待重新分配”需要分清。
- 一次服务航点事件可能关联**多个同源订单**，应按显式订单清单标识，不能靠列表隐含顺序推测货物所有权。
- 事件应包括：`event_id`、`sim_time_s`、`kind`、`task_id`、`drone_id`、`before/after`（或足以重算的 delta）、`source/reason`；执行器发出服务事件，统计器只能消费已经提交的执行事件。

### 3.3 单步时钟：**当前实现**与**目标约束**分开写

当前 `Environment.step(actions)` 主要按 **接纳分配 → 推进时钟 → 新任务生成 → Drone.update 运动与扣电 → 航点服务完成 → 泊位仲裁 → 汇总统计** 的顺序执行（以实际 HEAD 为准）。现有 `WL-3` 规范已声明类似处理顺序。

不宜为了“常见仿真教材顺序”而擅改成“先生成新任务再分配”；那会改变任务生成时刻能否本步可见，以及全量 E0/E1 行为。

需要**对当前顺序**补齐以下明文契约：  
1) 在 `t` 时刻提交的动作只能使用该时刻已经可见的任务；2) `t+Δt` 新任务何时允许调度必须可判断；3) 取货/送达/换电在同一时间步相遇时，有确定排序与唯一服务事件；4) SLA 在恰好等于截止时间时的准时判据写死；5) 快照 `save → restore → step` 与连续执行的后续事件序列一致。

可使用离散步推进，不要求换成 SimPy；SimPy 的“同一时间戳事件确定排序”是**设计参考**，不是迁移建议。

## 4. 最小系统不变量（所有合法状态迁移后都应成立）

| ID | 不变量/等式 | 检查方式 |
| --- | --- | --- |
| INV-01 任务分区 | `N_generated = N_pending + N_assigned + N_in_transit + N_delivered + N_failed + N_cancelled`；互斥且覆盖全集（“重排队”应映射回非终态，不双算） | 逐订单 ID 集合分区，核对全局注册表与已完成事件 |
| INV-02 唯一所有权 | 一个未完成订单在一个时刻至多一个执行所有者；合法交接必须形成转移证据 | 取货/交接事件序列 + `task_id` 唯一性 |
| INV-03 取货先于送达 | `DELIVERY_COMPLETED` 必须有同一订单既往合法取货及当前送达事件 | 异常轨迹与人工构造未取货送达反例 |
| INV-04 货物守恒 | 已取未送货物 = 各在机/已交接保管方库存的按 ID 不重不漏之和 | 按订单货物身份与重量双对账，而非仅检查总 kg |
| INV-05 电池账本 | `B_after = B_before − flight_debit − other_debit + recharge_or_swap_delta`；`0 ≤ B ≤ capacity`；飞行可行性门不得允许欠电却有实际位移 | 每步扣电原因与里程独立求和；换电作为单独事件 |
| INV-06 泊位守恒 | `0 ≤ occupied_station ≤ berths_station`；同一换电会话只有一个有效泊位 | 机巢竞争、关闭、故障、释放反例 |
| INV-07 运动与障碍 | 每步实际位移 `≤ speed × Δt`；位置与路径必须服从**本模型**的几何约束；不把可视化 z 当真实高度 | 路径/地图控制组与撞障反例 |
| INV-08 统计一致 | `completed_count = count_unique(valid_delivery_event.task_id)`；与任务终态一致，不能只复制同一计数器作为“独立核验” | **独立重放**事件 → KPI 与在线累计比较 |
| INV-09 过程可解释 | 任一拒绝、取消、冻结、改道、重分配都有确定原因及后续处理，不能静默吞单 | 事件 ID、原因、剩余任务清单及失败注入 |

INV 是**建议验收规格**，不是“所有规则当前已实现”。与现有 `docs/端到端一致性门设计.md` 的 I1–I5/EG-1–EG-6 交叉映射，验收时沿用原编号/判据，避免重复造门。

## 5. 指标口径：定义分母、窗口和未完成

| 指标 | 推荐精确定义 | 注意 |
| --- | --- | --- |
| 全任务完成率 | 截止观察时刻合法送达的唯一订单数 / 已生成订单数 | 未完成必须保留在分母 |
| 已完成订单超时率 | 已完成且晚于截止时间的订单数 / 已完成且定义了截止时间的订单数 | **条件超时率**，不能代替整体服务失败率 |
| 到期未按时服务率 | 已到期且在截止前未完成的订单数 / 已到期订单数 | 明确是否包含已逾期后最终送达；二者均视为未按时服务 |
| 全任务按时完成率 | 在截止时间（含边界）前完成的订单数 / 已生成且有截止时间的订单数 | 观察窗末未到期订单是**截尾**，不能直接称超时 |
| 生成到完成时间 | `completion_time − generation_time`，仅对合法已完成订单报告 | 同时报告未完成与平均在系统等待时间 |
| Wh、换电、里程 | 由运动/换电事件账本独立累加，按单/按公里指标须写明分母 | `assigned` 与 `onboard` 策略分开记录，不混图比较 |

当前 `frontend/environment.py::get_statistics` 的 `timeout_rate = 1 - total_on_time_tasks/total_completed_tasks` 表示**已完成订单中的非准时比例**；零完成时返回 0。它不是全任务超时或失败率。应保留历史字段兼容及原指标定义，在新字段中明确增补“到期未服务”和“未完成”指标，不直接改写冻结实验的解释。

## 6. 调度器与环境如何真正实现同一个“世界”

建议契约：

`固定外生订单流/场景 + 世界状态 → Scheduler.predict()/act() → 环境动作准入 → 真实执行事件 → 状态/账本 → 指标`。

- Greedy、GA、PSO、OR-Tools **可以**使用不同启发式和近似目标；但每个算法必须在**同一环境执行约束**下受评。
- 调度器可用直线距离估计，执行器用 A* 绕障；这属于**建模间隙**而非天然 bug。必须分列记录 `predicted_eta_s`/`actual_eta_s`、`predicted_energy_wh`/`actual_energy_wh`、失败与重调度原因。
- 调度器输出非法动作时，环境必须统一拒绝并产生可审计原因，不得“跳过后悄悄丢单”或“虚构成功”。
- 资源紧张、不可达、低电、故障和任务链约束在执行侧必须是**硬约束**；算法可自由选择其近似求解策略，但不得绕过硬约束。
- 不把内部 `fitness` 在不同算法间直接比较为同一个目标值：PSO 加权准时/时延/能耗，GA 链式解码代价与 OR-Tools makespan/tardiness 目标具有不同定义。**只比较独立统一执行后的 KPI**，并披露每种算法求解的代理目标。
- 固定共同外生场景，不仅仅“固定相同 seed”：订单输入流、天气扰动/故障等外生事件应预生成或采用独立命名 RNG，避免算法随机搜索消费随机数改变后续订单。

## 8. 验证方法：不是测试互相抄答案

1. **已知答案（Oracle）**：一机一单、无障碍、可人工算出运动时间和理论 Wh，作为极小控制组。
2. **状态/资源不变量**：在每次状态迁移后检查 INV-01–09，不只在整回合终止检查。
3. **故障与突变注入**：无取货伪送达、同单两机占有、非法超载、飞行电量不足、机巢超泊位、临界截止时间、断点恢复。
4. **真变异测试（RED 牙）**：人工制造错误，要求**被测检查真正失败**；不能只检查“伪造的数据比原来不同”就称为通过。
5. **独立重算**：事件日志与任务/电池/泊位当前状态独立对账；不能用同一函数自我调用两次制造“第二证人”。
6. **一致性/变形测试**：零风 E1 与 E0 的合法等价范围、载荷单调、同输入确定性；注意历史 `[E0_MILEAGE_SCOPE_INCOMPARABLE]` 范围限制。
7. **实验配对**：固定订单流、地图、机队、初始状态及外生扰动；记录真实 `optimize_calls`、任务数、失败率、统计区间；比较实际执行 KPI，而不是单纯优化器内部分数。
8. **模型适用性**：有可追溯原始飞行数据后，再按**整次飞行**留出和分工况报告误差；不同机型不能直接移植绝对 Wh/km。

## 9. 执行路线：先逻辑闭环，再可信性

| 阶段 | 工作范围 | 成功判据（预注册，未执行前不得打勾） |
| --- | --- | --- |
| **L0 只读审计** | 固定新实验基线；映射订单/无人机/机巢状态写入点、读者和关键事件；冻结反例与证据 | 有状态图、写入点表、风险清单；明确哪条证据缺失 |
| **L1 生命周期** | 先红测试，消除 `is_free` 导致的无送达完成，统一 `Task.status`、任务归属与货物保管 | 无合法 `DELIVERY_COMPLETED` 不能增加 completed；同源多单、故障/换电/改道全部通过 |
| **L2 指标对账** | 保留历史指标，新增未完成、已到期未服务、截止时截尾定义，事件独立重算 | 在线指标与独立重算相等；无完成但全部到期的情景不会显示整体失败率 0% |
| **L3 动作准入** | 环境统一核对动作合法性，拒绝与重排队有事件原因 | 四算法及非法动作生成器共用一套最终判据；拒绝不导致订单消失 |
| **L4 Plan vs Actual** | 为候选决策、实际运动、换电/延误添加配对记录 | 每笔可关联预测与执行；误差分布、失败原因和回退逻辑可追溯 |
| **L5 研究/实测** | 固定外生场景、配对统计；按用途决定是否进入 CMU/同机型实飞标定 | 首先满足 L0–L4，不发表超出外部证据范围的结论 |

工作纪律：**独立研究分支 → Draft PR → RED → 最小修复 → GREEN → 继承回归 → 精确 HEAD 九 Job 全量成功 → 恢复原 base/API 回读**。不得为了绿色 CI 删除反例、放宽硬断言或污染冻结 E0/E1、`master`。

### L0 第一轮最小交付（现在最值得做）

- 建一个 `docs/logic-audit/` 风险矩阵：不变量 ID、权威字段、写入点、读取方、独立证据、已覆盖/未覆盖、失败反例。
- 列出 `Task.status`、`drone_assignments`、`completed_tasks`、`total_completed_tasks`、`onboard_load_kg` 的所有写入/消费链。
- 针对 `is_free` cleanup 构造**真的执行至该分支**的独立负面测试；优先不要改变代码。
- 针对“生成 100、送达 40、全部按时”的指标样例，证明当前 `timeout_rate`=0 只是**已完成订单条件超时率**，并确定新指标如何表达未服务。
- 确认 L1 修复范围、行为兼容性、回归测试与不合并纪律，才允许实施生产改动。

## 11. 最终准则

> **仿真系统的可靠性不是“运行了许多真实地图/数据”，而是“规定的对象、事件、时间、资源和指标能够在同一个世界中互相证明、互不矛盾”。**
>
> 验证这套规则真的被正确实现，再确认它对现实问题是否适用，最后才允许对算法收益给出有边界的结论。
