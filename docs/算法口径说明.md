# 算法口径说明：申报方案与实现范围的对应关系

> 用途：结项 / 中期检查时，用于说明「项目申请书承诺的算法」与「代码实际实现的算法」
> 之间的对应关系，以及为何在实现过程中扩展了对比范围。
> 建议作为结题报告的附录，或在答辩时作为口径说明页。

---

## 一、结论速览

项目申请书规划了**三种对比方案**：贪心基线、经典求解器（OR-Tools）、本项目优化算法（遗传算法）。

代码实际实现并纳入统一评测的是**五个系列**：

| 算法 | 项目书是否提及 | 实现状态 | 说明 |
|---|---|---|---|
| Greedy 贪心基线 | ✅ 明确 | 已完成 | `scheduling/greedy/` |
| OR-Tools 经典求解器 | ✅ 明确 | **本次补齐** | `scheduling/ortools_scheduler.py`（CP-SAT 降维求解） |
| GA 遗传算法 | ✅ 明确（主推） | 已完成，需复跑 | `scheduling/ga_scheduler.py` |
| PSO 粒子群 | ❌ 未提及 | 已完成 | `scheduling/pso_scheduler.py` |
| MARL 多智能体强化学习（IQL/VDN/QMIX） | ❌ 未提及 | 已完成 | `backend_wx/pymarl-master/` |

**没有删减任何申报内容，只做了扩展。** 下面说明扩展的理由与公平性保障。

## 二、为何在申报方案外增加 PSO 与多智能体强化学习

### 2.1 PSO（粒子群优化）

申请书中「（二）核心调度算法实现」的原文是：

> 任务链优化引擎：采用**启发式群体智能优化算法**，结合约束感知的任务序列构造方法……

「启发式群体智能优化算法」是一个**算法族**的表述，遗传算法与粒子群算法同属该族。
在实现阶段把两者都做了出来，原因是：

1. **GA 与 PSO 共享同一套适应度函数与物理口径**（`fitness_evaluator.py`、
   `PSOOptimizer.evaluate_fitness`），实现 PSO 的边际成本很低，且能直接回答
   「同族算法中哪一种更适合本问题」这一立项时无法预判的问题；
2. 两者都复用**同一套双通道事件驱动框架**（`PSOScheduler`），`GAScheduler` 直接
   继承 `PSOScheduler` 仅替换批量优化器，因此二者对比是严格的控制变量实验；
3. 结项报告需要回答「本项目算法相对基线有多好」，多一个同族参照能让结论更稳健。

### 2.2 多智能体强化学习（IQL / VDN / QMIX）

1. 申请书「四、项目实施方案（五）成果总结与推广」提出**发表学术论文 1 篇**。
   仅对比贪心 / GA / OR-Tools 属于课程作业级别的实验规模，难以支撑论文发表；
   引入 PPO 类的 MARL 对比能体现方法的先进性；
2. 项目创新点之一是「机巢地面资源约束下的动态调度」，这本质是**多智能体协同决策**
   问题，MARL 是最自然的建模方式，与项目主线一致而非另起炉灶；
3. 强化学习部分完全建立在既有仿真环境之上（`backend_wx/pymarl-master/src/envs/env_drone.py`
   直接复用 `frontend` 的 `Environment`），没有额外增加硬件或数据需求，
   与申请书「研究全程为纯软件仿真，无物理设备需求」的定性不冲突。

## 三、公平性保障（这是扩展对比能否成立的关键）

所有算法共用**同一物理口径**与**同一评测口径**，差异仅在于「缓冲区批量分配用哪个算法」：

1. **同一仿真环境**：均由 `simulation/environment.py` 驱动，1 step = 1 秒、
   异构机型参数、机巢整组换电 180 秒、任务生成分布完全一致；
2. **同一事件驱动框架**：PSO / GA / OR-Tools 三者共用 `PSOScheduler` 的双通道
   （直通 + 缓冲）与空闲机即时抽取逻辑，仅 `_build_optimizer()` 不同；
3. **同一机内排序**：单机内部任务执行顺序均由 `_dynamic_greedy_reorder()` 决定，
   PSO / GA / OR-Tools **不参与排序决策**，因此排序能力不构成差异；
4. **同一随机种子**：统一使用 `seed = 100 + episode_id`，四类算法跑的是同一批任务场景
   （此前 Greedy 未传 seed，导致场景不对齐，本次已修复）；
5. **同一指标口径**：统一由 `app/metrics_schema.py` 定义列，写入
   `results/compare/*.csv`，由 `results/plot_compare_metrics.py` 汇总。

## 五、OR-Tools 基线的建模口径

申请书原文：

> 对比基线：搭建贪心调度基线……并集成 OR-Tools 求解器作为**经典 VRP 降维求解**的性能参照。

实现要点（`scheduling/ortools_scheduler.py`）：

- **求解器**：CP-SAT（约束规划），每次批量分配限时 2 秒，超时取当前最优可行解；
- **决策变量**：任务 → 无人机的 0/1 分配；
- **硬约束**：
  - 每任务恰好分给一架机；
  - 异构载重上限（含环境 `multi_task_max_total_weight` 校验口径，避免被环境静默拒单）；
  - 各机就绪时刻 `ready_time`（忙碌机先清完在手工作）；
  - 异构速度换算（各机型真实 speed → env-step）；
- **目标函数**：`minimize makespan + Σ 超时量`，与申请书
  「构建以**最小化总任务完成时间**为目标的优化模型」一致；
- **降维方式与 PSO / GA 一致**：忽略机内排序（由框架统一动态贪心决定）、
  用「最坏完成时刻」做时间窗校验，因此是公平对照而非削弱基线；
- **兜底**：求解器无解时退回批量贪心并打印告警，保证基线不崩、不劣于贪心。

## 六、需要说明的局限性

1. 强化学习效果依赖训练轮数、随机种子与奖励权重，不能依据单次训练结果判定优劣，
   结项时应报告多随机种子的均值与方差；
2. CP-SAT 每次求解限时 2 秒，大规模场景下可能只得到可行解而非最优解，
   报告中应注明 `status`（OPTIMAL / FEASIBLE）；
3. GA 的排列编码解码为**链尾贪婪追加**（`chain_codec.greedy_split_decode`），
   调度器侧支持「在途机顺路接入」（`PSOScheduler._dispatch_chain_insertions`），
   详见 README「任务链与顺路接入」一节；但**链内最优插入 / 2-opt / Or-opt 等
   局部搜索**尚未实现，进一步挖掘空间在结项材料中应如实说明；
4. 禁飞区已支持 `config/simulation.json` 静态配置（含 circle / polygon + 安全余量），
   参与路径规划与场景生成；但**动态禁飞区 / 时变管制**未实现。
