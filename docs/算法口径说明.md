# 算法口径说明：申请书与实际实现的对应关系

> 用途：大创中期检查、结项报告和答辩。项目实现允许在申请书基础上扩展，但申请书明确承诺的核心内容必须能够在代码、实验和演示中找到对应实现。

## 一、项目主线

本项目对外统一表述为：

**面向城市应急与低空物流场景的异构无人机集群三维协同调度仿真平台，通过“能力匹配 + 任务链优化 + 机巢资源动态调度”实现多无人机、多任务、多机巢条件下的联合优化，并用 Greedy、OR-Tools 等基线进行对比验证。**

申请书的三项核心技术要求与代码对应如下：

| 申请书要求 | 当前实现 | 代码位置 |
|---|---|---|
| 异构无人机能力—任务需求匹配 | 已实现并进入 GA 解码代价 | `frontend/matching.py`、`backend_si/chain_codec.py` |
| 排列编码 + 贪婪分割形成任务链 | 已实现 | `backend_si/ga_scheduler.py`、`backend_si/chain_codec.py` |
| 任务分配后局部搜索优化顺序 | 已实现 | `backend_si/chain_codec.py:local_search_chains` |
| 机巢起降/换电资源动态优先级 | 已实现 | `frontend/charging_station.py`、`frontend/environment.py` |
| 滚动任务到达与顺路接入 | 已实现 | `backend_si/pso_scheduler.py`、`frontend/environment.py` |
| Greedy / OR-Tools / 项目算法对比 | 已实现统一评测入口 | `frontend/evaluate_metrics.py` |
| 任务密度、异构配比、机巢泊位敏感性实验 | 已提供自动化脚本 | `run_conclusion.py` + `experiments/runner.py` |
| 三维可视化与指标展示 | 已实现 | `frontend/map_drawer_3d.py`、`console/` |

## 二、算法角色划分

申请书规划的是“贪心调度、经典求解器、本项目优化算法”三类方案。结项材料中建议固定以下层级：

| 算法 | 结项定位 | 说明 |
|---|---|---|
| Greedy | 基线 1 | 实时启发式调度，用于体现联合优化相对简单规则的增益 |
| OR-Tools | 基线 2 | CP-SAT 经典求解器，作为组合优化参照 |
| GA | **本项目主推算法** | 排列编码 + 贪婪分割 + 能力匹配 + 解码后局部搜索 |
| PSO | 扩展对比 | 与 GA 同属群体智能，检验不同群智能优化方式的差异 |

因此答辩时不应把项目描述成“核心是 MARL”。更准确的说法是：**申请书承诺部分全部保留，并在统一仿真平台上进一步增加了群智能（PSO）扩展对比。**

> **MARL（IQL / VDN / QMIX）已于 v1.0.1 整体移出本项目。** 原因不是效果不好，而是其对比数字无法追溯：逐格核对 6 算法 × 9 指标 = 54 个性能格后，23 格优于该算法历史最好一局、0 格劣于最差一局、38 格与原始记录中任何一行都不相等，且训练产物从未进入版本库。证据见 [`数据来源与可追溯性登记表.md`](数据来源与可追溯性登记表.md) 第五节 R2，可用 `python verify_data_provenance.py --marl` 复算。**结项材料不得再引用任何 MARL 指标数字。**

## 三、主推 GA 的实际流程

当前 `ga.encoding=permutation` 时，完整流程为：

```text
待调度任务
   ↓
GA 排列染色体
   ↓  OX 交叉 + swap / insert / reverse 变异
候选任务排列
   ↓
约束感知贪婪分割
   ├─ 载重硬约束
   ├─ 电量安全余量
   ├─ 时间窗 / 超时容忍
   └─ 能力匹配代价（载重/体积、速度/时效、续航/距离）
   ↓
每架无人机的有序任务链
   ↓
解码后局部搜索
   ├─ 链内 swap
   ├─ 链内 relocate
   ├─ 链内 reverse / 2-opt 邻域
   ├─ 链间 relocate
   └─ 链间 swap
   ↓
完整约束回放校验
   ↓
最终调度任务链
```

GA 的链级代价为：

```text
Cost = makespan
     + w_tardy × total_tardiness
     + w_dist × total_distance
     + w_match × Σ(1 - capability_match)
     + w_unassigned × unassigned_count
```

其中能力匹配度按任务类别动态调整权重：急件更强调速度，重货/大体积任务更强调载重，长距离任务会体现续航适配。这样“能力匹配”不再只存在于前端 Greedy 或即时派单逻辑，而是正式进入 GA 的优化目标。

### 关于载重口径

任务链表示“完成前序任务后顺路接入下一任务”，因此任务完成并送达后货物会卸载。链级解码按逐任务取送执行，**不会把整条链所有任务重量永久累加**。这与申请书的“单机多任务执行顺序”语义一致，也避免出现一架 10 kg 无人机无法依次执行两个 8 kg 任务的错误约束。

## 四、能力匹配口径

匹配函数主要由三部分组成：

- **载重/体积匹配**：货物所需运力接近无人机有效载荷时得分较高，超载仍由硬约束直接排除；
- **速度/时效匹配**：deadline 越紧、优先级越高，高速机的优势越明显；
- **续航/距离匹配**：根据电池容量与单位距离能耗估算经济航程，长距离任务优先匹配续航更合适的机型。

`frontend/matching.py` 与 `backend_si/chain_codec.py` 采用同一计算思想。此前速度归一化参考值为 320 m/s，会把 14~20 m/s 的真实机型速度差异压缩到几乎不可见；现已按本项目机型范围校准为 25 m/s。

## 五、局部搜索口径

申请书明确提出“任务分配后使用局部搜索优化执行顺序”。当前实现是在 GA 得到最优排列并完成贪婪分割后，对最终任务链做 best-improvement 搜索。

每个候选邻域都重新推进完整时间轴并检查：

1. 单机载重是否可行；
2. 电量是否满足安全余量；
3. 是否需要先去机巢换电；
4. deadline 超时是否超过容忍范围；
5. 新任务链的综合代价是否真正下降。

局部搜索只对最终 GA 解运行，而不是对种群中每条染色体运行，避免 `population_size × generations` 级别的计算量放大。运行统计会给出 `local_search_before_cost`、`local_search_after_cost`、`local_search_improvement` 和候选评估数，可用于答辩展示“局部搜索确实生效”。

## 六、公平性说明

对比实验应遵循“相同场景、相同随机种子、相同物理环境、相同指标”的原则：

1. 所有算法均运行于 `frontend/environment.py`；
2. 异构机型参数、任务生成、机巢、换电、禁飞区等环境条件一致；
3. 同一组实验使用相同 `seed`；
4. 指标统一由 `frontend/metrics_schema.py` 导出；
5. Greedy、OR-Tools、GA 的核心差异是调度决策方式，不人为改变任务或无人机物理参数。

需要注意：GA 排列编码会保留其优化后的链内顺序，因此**不能再声称 GA / PSO / OR-Tools 三者使用完全相同的机内排序规则**。这不是“不公平”，而是 GA 主推方法本来就包含申请书承诺的“任务链时序优化”；公平性来自场景和约束一致，而不是强行抹掉算法本身的能力差异。

## 七、结项控制变量实验

结项数据由 `run_conclusion.py`（编排）+ `experiments/runner.py`（执行与聚合）生成，每个组合在独立子进程、独立 `simulation.json` 副本中运行。默认主比较只跑：

```text
Greedy / GA / OR-Tools
```

并自动进行三类敏感性测试：

- `task_density`：只改变任务到达间隔缩放，观察任务密度影响；
- `fleet_mix`：保持 10 架无人机，只改变轻载/标准/重载机比例；
- `nest_berths`：只改变每个机巢泊位数 1/2/3。

运行：

```bash
cd frontend
python run_conclusion.py --preset quick
python run_conclusion.py --preset conclusion
```

输出位于 `results/experiments/<预设>_<时间戳>/`，包含 `raw_runs.csv`、各聚合 CSV、`summary.md`、`experiment_config.yaml` 与 `reproducibility.json`（复现清单，schema v2：按算法登记实现源码哈希、输入路径一律相对仓库根）。脚本通过环境变量加载临时配置，不会覆盖主 `simulation.json`。

## 八、PSO 的扩展理由

PSO 与 GA 同属群体智能优化，适合作为同类算法的扩展参照，检验不同群智能优化方式的差异。

扩展算法的存在不改变项目主线：**GA 是申请书对应的主推优化算法，PSO 是平台能力扩展和实验补充。**

## 九、仍需如实说明的局限

1. 禁飞区目前是静态配置，未实现时变空域管制；
2. 仿真未加入天气、通信丢包等真实低空随机因素；
3. OR-Tools 每次批量求解有时间上限，大规模场景下可能返回 FEASIBLE 而非 OPTIMAL；
4. ~~MARL 的比较结论必须报告多随机种子均值/方差~~ —— MARL 因数字不可追溯已整体移除，不再适用；
5. 当前局部搜索基于欧氏/仿真估计代价，最终真实执行仍以环境路径规划和离散时间步为准。

## 十、答辩建议一句话

> 我们没有改变申请书的研究目标，而是把申请书中的“异构能力匹配、任务链时序优化、机巢资源调度”落实成统一仿真平台；主推 GA 采用排列编码、约束感知贪婪分割和解码后局部搜索，Greedy 与 OR-Tools 作为基线，PSO 作为实现阶段扩展对比。

## v1.0 实验结果解释口径

正式结项实验除均值外同时保留标准差、中位数以及原始 Seed 级结果。GA 与 Greedy 的 `paired_ga_vs_greedy.csv` 使用**相同 Seed**做描述性配对，用于减少任务随机生成差异对横向解释的干扰；其中“平均改进”按指标方向统一为“正值代表 GA 更好”。

这张表只用于**描述性分析**，不应口头或书面表述为“统计显著”。如果某个场景中 Greedy、OR-Tools 或 PSO 在某项指标优于 GA，应如实报告，并结合任务规模、约束强度、算法时间预算解释，而不是删除不利实验或改变指标定义。
