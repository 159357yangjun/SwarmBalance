# 调度预测口径 vs 执行口径（Q1 审计）

> 取证方式：主线程逐条读取原文（不采信子代理转述 —— Q1 子代理撞上限中断、零交付，
> 本文所有行号都是我本人打开文件读到的）。HEAD `94e3816`。**纯只读，未改任何行为。**

## 0. 一句话结论

**四个调度器全部按二维直线优化，没有任何一个查询 A\*。** 实际路线由 `env.step()` 生成。
⇒ 分裂真实存在；但它在各策略目标函数里的**权重差别极大**，不能一概说成"结论都不可信"。

## 1. 距离核清单（亲验）

| 位置 | 表达式 | 口径 |
|---|---|---|
| `frontend/environment.py:1507` | `route_distance = math.dist(source, destination)` | 任务内直线（喂观察空间） |
| `frontend/greedy/scheduler.py:29-32` | `euclidean_distance` = `sqrt((p1[0]-p2[0])**2 + (p1[1]-p2[1])**2)` | 机→取货点直线 |
| `frontend/greedy/scheduler.py:171-174` | `total_distance = source_dist + route_dist` | **两段都是直线相加** |
| `backend_si/chain_codec.py:92` | `math.hypot(a[0]-b[0], a[1]-b[1])` | GA / PSO 共用的里程核 |
| `backend_si/ortools_scheduler.py:119` | `math.hypot(p1[0]-b…, p1[1]-…)` | OR-Tools 自己的里程核 |
| `backend_si/ortools_scheduler.py:121-124` | `_travel_steps = distance / speed` | ETA：直线 ÷ 速度 |

## 2. 分策略矩阵

|---|---|---|---|---|---|

## 3. 关键限定：权重把误差压掉了多少

| 项 | 值 | 出处 |
|---|---|---|
| GA/PSO 代价里里程权重 | `w_dist = 0.01` | `backend_si/config.yaml:126`（覆盖代码默认 0.001） |
| 同式里超时权重 | `w_tardy = 2.0` | `:125` |
| 比值 | 里程项 ≈ 超时项的 **1/200** | `chain_cost:477-490` |
| Greedy 距离权重 | `DISTANCE_WEIGHT = 0.4`、`MATCH_WEIGHT = 0.6` | `greedy/scheduler.py:17-18, 188` |
| Greedy 匹配内部续航权重 | `range: 0.3`（÷ `DEFAULT_WEIGHTS` 总和 1.0） | `matching.py:11` |

⇒ **推论（必须与 §1 一起说，否则就是夸大）**：
- 对 **Greedy**：距离是显式打分项且占 0.4 权重 ⇒ 直线/A* 差异**能**改变分配结果，是最值得做 Gate C 实验的对象。
- 对 **GA/PSO**：**只能说"距离项系数显著小于 tardy 系数"，实际 fitness 贡献比例尚未验证。**
  系数比 0.01 : 2.0 不等于贡献比 —— 两项原始量纲与数值尺度不同。反例即用户给出的算术：
  `distance_term=3000, tardy_term=20` 时 `0.01×3000 = 30` 与 `2.0×20 = 40` 已接近同量级。
  ⇒ 结论待 objective term decomposition 实测（见 §7），在此之前不得写"1/200 所以不承重"。
- 对 **OR-Tools**：ETA 直接由直线推得（`:124`），若时限约束紧则可能误判可行 ⇒ 需要单独一轮验证，本轮**未确证**。

> ⚠️ 本文此前版本写过"里程项 ≈ 超时项的 1/200"以及"GA/PSO 当前不承重"，那是把**系数之比**
> 当成**加权贡献之比**的推理错误（同一族里我第三次犯：空载比满载、行扫描当元素计数、这次是权重）。
> 已按实测口径改写；正确做法是先量出各项加权后的真实占比再下结论。

## 4. 「调度认为 A 近、实际 A* 反而更远」是否结构性可能？

**是，且给出可复算条件**：Greedy 的 `total_distance` 含 `source_dist`（机→取货点），
这一段在执行时同样要走 A*（`environment.py:1800` 规划 current_pos → source）。
所以只要两架机的直线路径中有一条被高楼截断，排序就可能翻转：

```
Drone A：直线 1.8 km（被楼挡，实飞 3.7 km）
Drone B：直线 2.2 km（畅通，实飞 2.2 km）
现系统按 1.8 < 2.2 选 A；按真实航路应选 B
```

这不是假想：`environment.py:1847` 的 `if self.is_path_clear(start, end): return [end]` 说明
**大量请求确实走直线短路**，只有被挡时才进 A* ⇒ 分歧集中在"被楼挡住的少数航线"上，
而 Greedy 对这少数也按直线计价。

## 5. 抽离边界（步骤 2 的前置证据）

A* 区段（`environment.py:1842-2024`，6 个方法）只依赖 Environment 的 **6 个成员**：

```
self.heuristic            ×4   （h / g 增量 / 终止判据，见 :1910/1918/1933/1938）
self.no_fly               ×3   禁飞区集合
self._high_buildings_bbox ×3   障碍几何预计算
self.is_path_clear        ×2   自身递归
self._path_clear_cache    ×2   结果缓存
self.total_no_fly_detours ×1   ⚠ 计数器：副作用，抽离时要决定归属
+ high_buildings / _path_clear_bucket / _is_path_clear_uncached / _PATH_CLEAR_CACHE_MAX
```

⇒ 耦合面远小于 2024 行的体量所暗示的范围，**抽离可行**。
两个必须在 Phase 1 处理的点：
1. `total_no_fly_detours`（`:1852`）是路径规划顺手写的统计副作用 ⇒ 抽离后应由调用方记录，
   否则 RoutePlanner 变成有状态的隐藏写入者。
2. `is_path_clear` 实测被调 18 万次 / A* 仅 34 次（`:1983-1984` 原注释）⇒ 缓存与世界指纹
   （`:1961-1967`）必须随模块一起搬走，不能留在 Environment 里再跨对象回调。

## 7. Objective term decomposition —— 已实测（`docs/取证输出/objective_term_decomposition.txt`）

只读探针 `console/objective_term_probe.py`：monkeypatch `chain_cost` 为透传记录版（返回值逐字不变），
走 `experiments/worker.run_one` 真实调用链，seed 40901，C-1/C-2 × GA/PSO。阈值预先写在脚本头部。

| 项（加权后） | GA × C-1 | GA × C-2 |
|---|---|---|
| `w_makespan × makespan` | **54.0%** | 8.6% |
| `w_tardy × total_tardiness` | 17.2% | 8.9% |
| `w_dist × total_distance` | **8.4%**（中等） | **1.0%**（次要） |
| `w_unassigned × unassigned` | 11.8% | **80.5%** |
| `w_match × total_match_score` | 8.7% | 0.9% |
| chain_cost 调用次数 n | 200000（⚠ 撞采样上限被截断） | 166918（完整） |
| PSO 两格 | **n=0 ⇒ 本格作废**（优化器未被调用，与 `optimize_calls=0` 独立复现一致） | 同左 |

结论（替换掉 §3 里那句错误的"1/200"）：

1. **系数之比确实推不出贡献之比**，而且比预想更强：同一个 `w_dist` 项在两格里差 8 倍
   （8.4% vs 1.0%），原因是分母被别的主导项吃掉 —— C-2 里 `unassigned` 罚项占 80.5%。
2. **距离口径分裂的真实定位**：在 C-1 属【中等】(8.4%)、在 C-2 属【次要】(1.0%)。
   ⚠️ **但这个比例不能用来预测 Phase 1B 的 KPI 变化幅度**（此处为二次纠正，见 §8）：
   它只度量"当前 GA、当前候选解、当前欧氏模型下 distance term 的直接加权贡献"。
   route-aware 成本会经由候选排序 → 任务链 → makespan/tardiness/feasibility/unassigned
   产生**间接且离散**的影响 ⇒ 1% 也可能因一次分配翻转造成大变化；
   反之 8.4% 也可能因为多数路线本就 `is_path_clear` 直达而几乎无差异。
3. **主项其实是 makespan（C-1 54%）与 unassigned（C-2 80.5%）**，不是超时也不是里程。
   ⇒ 目标函数当前的真实重心是"做完 + 别漏单"，这修正了我此前对 GA/PSO 优化目标的描述。
4. PSO 无读数 ⇒ 关于 PSO 的任何 fitness 归因本轮**不成立**，须等双通道介入问题（P0#2/#3）解决后再测。

探针自身的已知缺陷（如实记，不影响上表方向但影响其完备性）：GA×C-1 触到 `CAP=200000` 采样上限，
该格占比是"前 20 万次调用"的样本而非全体；已在输出里打 ⚠。提高 CAP 或改为在线累加（只存和与平方和）
是后续动作，本轮不改。

要回答的问题：代表性 C-1/C-2 运行中，GA/PSO 的 objective 各组成项**加权后**实际贡献多少。

```
w_makespan * makespan
w_tardy    * total_tardiness
w_dist     * total_distance
w_unassigned * unassigned
w_match    * total_match_score
```

真源：`backend_si/chain_codec.py:477-490`（`chain_cost`）。诊断方式：在 `chain_cost` 外包一层
只读记录器，累加每次调用的各加权项与总代价，输出占比；不改任何返回值、不改权重。

判据写法（避免又变成一个形容词结论）：
- 打印每项的 mean/max 加权贡献与其占总代价的比例；
- 若 `w_dist*distance` 占比 < 5% ⇒ 分裂对 GA/PSO 属次要项；
- 若 ≥ 20% ⇒ 属核心问题，Phase 1B 的收益预期要相应上调；
- 区间内如实报"中等"，不硬贴标签。n 与调用次数一并打印（占比来自多少次 chain_cost 调用）。

## 8. 对 §7 结论 2 的自我纠正（用户指出，接受）

我在报告 Phase 1A 时写过"C-1 8.4% ⇒ 1B 收益较大；C-2 1.0% ⇒ 预计几乎不动"。
**该推断不成立并已撤回。** 占比是"目标函数里这一项的直接权重份额"，不是"替换该项后系统输出的敏感度"。
两者之间隔着一条离散链路：真实航路变长 → 候选排序改变 → 任务链重排 → makespan/tardiness 变
→ 部分任务转为不可行 → unassigned 变。任何一环上的单次翻转都能把 1% 的输入差放大成显著 KPI 差；
反过来若绝大多数 OD 对本来就直达，则 8.4% 也只是零差异。

⇒ 因此 Phase 1B 的第一步不是替换成本，而是 **1B-0 Route discrepancy profiling**：
直接量 Euclidean 与 RoutePlanner 距离的分布差异，并重点量 **candidate/ranking inversion**
（欧氏排序与实际航路排序发生翻转的候选对数与比例）。后者比"平均多绕 x%"重要得多，
因为它才是会改分配的那个量。
