# 证据等级与 Validation 边界

> 生成方式：本文所有数字均为**本轮亲自重跑/重解析得到**，每条附复算命令。
> 取证时间：2026-10-06（本机 `.venv310` / Python，网络为 curl 直连 Zenodo API）。
> 本文只回答一个问题：**当前项目的数据可信到什么程度，以及"再往上抬一级"需要什么。**

## 1. 一句话结论

**当前证据等级 = 「官方规格派生」（spec-derived），没有升到「实机数据独立验证」（hardware-validated）。**

这不是措辞谦虚，是被实测卡住的：Validation 路径已经走完并取得外部日志，但那批日志是仿真器输出，
用它算出的 Wh/km 只是把模型自己的假设读回来一遍 —— 那会产出一个**自洽的假验证值**，比不验证更坏。
所以 §5-D 保持「未锚定」，本文记录的是"为什么停在这里"，不是"下一步就能验证"。

三档口径必须分开讲，混一档就是夸大：

| 档位 | 含义 | 本项目现状 |
|---|---|---|
| **内部一致性** | 产物能被同一份代码逐位重算出来 | ✅ 已达成（两条 `--verify` 门 RC=0，套件绿） |
| **外部可回溯** | 每个被当作事实的数字能点回一个来源 | 🟡 **大部分达成**：厂商规格/OSM/气象接口均可回放；但 PX4 数据集那份 manifest 的**原始计算者未确认**（§4.1-bis），日志全量分类也**未完成**（§4.1-ter） |
| **实机有效性** | 数值与真实飞行物理量对得上 | ❌ **未达成**，且当前无可用通道 |

## 2. 已锚定（有外部来源，可点开、可复算）

能耗这条链是项目里唯一有官方外部输入的定量链。它的全部外部输入只有 **三个官方数字**：

| # | 外部输入 | 来源 | 等级 |
|---|---|---|---|
| 1 | 单块电池 **1984.4 Wh** | DJI FlyCart-30 官方规格页（DB2000 智能飞行电池） | A / Partial |
| 2 | 空载航程 **28 km** | 同上官方规格页 | A / Partial |
| 3 | 满载航程 **16 km**（载 30 kg） | 同上官方规格页 | A / Partial |

由这三个数派生出项目参数（复算命令见下）：

```
E   = 1984.4 × 2          = 3968.8 Wh        → config: battery_capacity
轻载 = E ÷ 28 km           = 141.743 Wh/km    = 0.141743 Wh/m → config: consumption_base (现值 0.142，差 0.18%)
满载 = E ÷ 16 km           = 248.05  Wh/km
载荷系数 = 28 ÷ 16         = 1.75             → config: battery_load_penalty_factor
```

```bash
# 复算（唯一外部输入是 1984.4 / 28 / 16 三个官方数）
python -c "E = 1984.4 * 2; print(E, E / 28.0, 28.0 / 16.0)"
#   3968.8 | 141.74285714285714 | 1.75
```

**已锚定的其它项**（详见 [`真实性审计表.md`](真实性审计表.md) §1、§2）：

| 对象 | 外部来源 | traceability |
|---|---|---|
| 地图碰撞体（建筑/道路/禁飞区几何） | OSM 底图原件 + sha256 在仓内 | **Complete**（离线可复算普查） |
| 机型速度/载重档 | DJI / 顺丰丰翼 ARK40 官方产品页 | Partial（厂商改版即失效） |
| 风速量级 | Open-Meteo Historical Weather API（再分析格点，默认 Best Match 混合，**未指定模式**） | Partial |

⚠ 厂商网页一律只给 **Partial**：判据是"核验是否依赖别人在线"，不是"此刻 curl 得通"。

## 3. 未锚定（纯内部推导，无外部依据）

| 代号 | 对象 | 现状 | 为什么不能算已锚定 |
|---|---|---|---|
| **D** | 能耗模型的**结构形式**（线性、按距离、无悬停项、无加减速项） | **未锚定** | 全仓**零拟合实现**（见 §4 的普查读数）。0.142 只是"官方两个数相除"，它锚定了**斜率的量级**，没有锚定**公式形状**。真实飞行包线含悬停/爬升/风阻，本模型把它们全折进每米常数。 |
| — | `battery_load_penalty_factor = 1.75` | **半锚定** | 28÷16 是官方数的除法，但"用航程比当功率比"这一步是我的假设：航程受容量/重量双重影响，不纯是功率。第三方交叉证据（悬停 29 min 空载 vs 18 min @30 kg ⇒ 功率比 ≈1.6）落在同量级，仅此而已。 |
| — | 能力匹配权重（载重/速度/续航加权） | **未锚定** | README §已知局限 已声明"仍需通过敏感性实验标定"。 |
| — | 绕行半径 1500 m | **未锚定** | 绝对半径随地图尺度变化，换图需重标；当前取"图跨度 55%"是本地选择。 |
| — | 需求到达过程（任务生成速率/优先级分布） | **部分锚定** | 结构取自即时配送常识，参数无运营数据支撑。 |

### T8 环路普查结论（关键，别把它读成"四条都验证过了"）

上面四个派生量（3968.8 / 0.142 / 1.75 / 248）**不是四条独立证据，是同一组官方数被除了四次**。

具体地：`0.142 × 1.75 = 248` 这个"吻合"是**恒等式**——
`(E/28) × (28/16) = E/16`，28 直接约掉，右边正是同一个派生量本身。
用精确分数（`fractions.Fraction`）验过相等，因此它**不提供任何新信息**。
旧文档把它写成"自洽校验通过"，会被读成"通过了一次独立验证"，T8 已订正为恒等式并标注非校验。

⇒ 推论：**本项目不存在标定（calibration）环节**，只存在规格派生（spec-derived anchor）。
对外表述必须用后者。

### 3-bis 已存在的外部交叉校验（别把 §3 读成"未锚定项一个外部数都接不上"）

写这份总结时我自己差点漏掉：手算量级核对其实**已经做过两次**，而且用的都是官方直接发布的值，
不是航程除法。它们仍属 B 类间接推算（官方没公布功率瓦特数），但**独立于 consumption_base 那条链**。

| 待检量 | 项目取值 | 外部一手输入 | 对撞结果 | 复算 |
|---|---|---|---|---|
| `battery_load_penalty_factor = 0.75`（⇒ 满载功率 ×1.75） | 无厂商公布依据，曾被记为"纯假设" | 官方**悬停时长**：空载双电 29 min、载 30 kg 18 min（同一块 3968.8 Wh） | 平均悬停功率 **8211 W vs 13229 W ⇒ 比值 1.61**，项目隐含 **1.75** ⇒ 同量级、略偏保守 | `python -c "E=1984.4*2; print(E/(29/60), E/(18/60), (E/(18/60))/(E/(29/60)))"` |
| 风能耗系数 `K_HEAD` / `K_TAIL`（`frontend/drone.py:33-34`，默认 **0.0**，登记为 assumption） | 线性每 m/s 增量，上下界 0.5–3.0 | 官方巡航速度档 **20 m/s**（FlyCart-30 规格） | 逆风 20 m/s ⇒ 倍率 **1 + 20×K_HEAD**；要落在 [1, 3] 内 ⇒ **K_HEAD ∈ [0, 0.10]/(m/s)**，这是官方数能给的**区间约束，不是点估计** | `python -c "print(0.0, 1+20*0.05, 1+20*0.10)"` |

两条限制必须一起说：
1. 悬停法给的是**悬停工况**的载荷功率比，本模型是**巡航**且按距离计费 ⇒ 只能校量级，不能校绝对值；
2. 风的约束来自"官方巡航速度是上界"这一条常识性推理，**没有任何厂商公布的风阻系数**，
   所以它只排除明显离谱的取值（如 K_HEAD=0.5 ⇒ 逆风 20 m/s 时 ×11），不排除中等取值。
⇒ 结论不变（§5-D 结构形式仍未锚定），但**"完全没有外部交叉检查"这句是错的**，在此订正。

### ⚠ 4.1-bis「是谁算的 MD5」—— 未确认（本节的结论被本轮实测驳回过一次）

上一版这里写的是"manifest 与 Zenodo 上的件逐字节相同 ⇒ 证人是外部的"。**这句现在是错的**，理由：

Zenodo 19617182 当前 `data.zip` 的中央目录有 245 条成员，其中**没有任何 `code/` 开头的文件**；
而仓内 `manifest.csv` 登记了 **9 个 `code/*`** 条目（含上游自己的打包脚本 `make_asi_dataset.py`、
`asi_extract.py`）。⇒ 这份 manifest **不是仅从 data.zip 生成的**。它登记的 `source_zip` 字段写着
`asi_runs.zip` / `asi-runs-2.zip`，但**那两个包此刻都不在手上、无法核对** ⇒ "manifest 覆盖的是那些上游原始包"
目前是**待验证的来源假设**，不是已证事实；能证的只有"它含有 data.zip 里不存在的成员"这一条否定式结论。

因此必须把三个问题分开，当前只答上了第一个：

| 问题 | 状态 | 依据 |
|---|---|---|
| **① 文件完整性**：本地件与登记的哈希是否一致 | ✅ **已证**（5/5 md5+尺寸吻合） | `px4_ulog_provenance.json` |
| **② 记录来源**：manifest 由谁、何时、依据哪些原始件生成 | ❌ **未确认** | manifest 含 data.zip 里不存在的 `code/*` ⇒ 非本记录产物；无任何上游生成脚本/日志可查 |
| **③ 样本类型**：内容对应真实飞行还是仿真 | 🟡 抽样的 **5/5 显示 SITL 特征**；其余 62 个未分类；**真实外场飞行数据：尚未确认** | 每个含 170 个 `SIM_*` 参数（§4.2） |

⚠ 措辞纪律（2026-10-06 用户指出，我原本把 ③ 标成了 ✅「数据真实性」）：上面三条**没有任何一条**证明"这是实机数据"。
已证的只有两件事——**样本完整性**（5/5 与登记 md5+尺寸一致）与**样本来源特征**（含仿真器参数指纹）。
对外只能写成：「样本完整性 5/5 核验通过；样本类型 5/5 显示 SITL 特征；真实外场飞行数据尚未确认」。
把 ③ 叫"数据真实性 ✅"会让读者以为我们验过真值方向，实际验的是"它是仿真的"。

同理，②的结论也要收窄一档：`code/*` 不在 `data.zip` 里，只证明 **manifest 不是仅由这个 ZIP 生成的**；
至于它是否来自 `asi_runs.zip` / `asi-runs-2.zip`，那两个包此刻都不在手上、无法核对 ⇒
那是**待验证的来源假设**，不是已证事实（我上一笔把它写成了"它覆盖的是…"，属越界，此处订正）。

唯一拿到的上游哈希级记录是 `data/manifests/ulog_manifest.txt`（585 B，md5 `78916e3746d4c657a1cd37c2013f1a23`
与 manifest 登记值逐位吻合，已存 `data/raw/px4_logs/upstream/`）——但它是 **E1–E5 × run01–05 = 25 条纯路径列表，不含任何哈希**，
所以它能证明"哪些日志被上游选入"，**不能**用来认定 md5 的计算者。

⇒ **写法要求**：对外只能说"本地文件与我们所获 manifest 一致"，不能说"经第三方校验"。
manifest 的来源属性记为 **「原始计算者未确认」**，除非将来能找到上游生成它的脚本运行记录。

### 4.2 为什么它仍然不算验证（决定性发现）

那 67 个日志是 **PX4 SITL + Gazebo 仿真器输出**，不是实机飞行记录。指纹在本轮重新测到（token 级扫描，绕开我一开始写错的报文分帧）：

| 文件 | `SIM_*` 参数数 | `SIM_BAT_DRAIN` | `SIM_BAT_ENABLE` | `SIM_GZ_EC_DIS*` |
|---|---|---|---|---|
| E1_openfield_sig4_seed002.ulg | 170 | ✅ | ✅ | 16 个 |
| E2_nearwall__run03.ulg | 170 | ✅ | ✅ | 16 个 |
| E3_corridor_sig4_seed001.ulg | 170 | ✅ | ✅ | 16 个 |
| E4_nearground__run01.ulg | 170 | ✅ | ✅ | 16 个 |
| E5_rooftop_edge__run01.ulg | 170 | ✅ | ✅ | 16 个 |

`SIM_BAT_DRAIN` / `SIM_BAT_ENABLE` 的含义是：**电池百分比由仿真模型按参数设定速率递减**。
也就是说这批日志里的电量数据本身就是"某个能耗假设的输出"。拿它反推 Wh/km，再把结果拿去"验证"我们的能耗假设，
是闭环引用自己的假设 —— 会得到一个看起来通过、实际什么都没证的数字。

⇒ **决定：不产出该数值。** 消费这些日志的唯一诚实用法是校"结构关系"（姿态/推力/速度之间的相关性），
而它们同样是模型内部关系，仍不及实机。

（附带记录一次我自己的取证弯路，避免下次重复误读：最初两次解析尝试报 `SIM_n=0`，
原因是我用 `b[:16]==magic+version+timestamp` 的定长假设和错误的报文步长去分帧，读到第 2 条报文就跑飞。
真实首条报文是 `'B'` flags（size=40），其后才是格式定义。结论必须以 token 级扫描为准。）

## 7. 冻结决定与下一阶段（2026-10-06 定）

**数据溯源审计自 `c76e8a5` 收口，本文件随之冻结**（后续只允许订正措辞，不再扩范围）。
下一阶段的执行载体是 [`Validation矩阵.md`](Validation矩阵.md)：逐子模型指定独立参照、验证指标、
判据冻结时点与适用范围；飞行物理子模型与协同调度模型的参照不可互相顶替。

**本文件与全部验证门自本笔起冻结**：不再新增 Verification 测试。
现有 290 + 32 项测试、两条 `--verify` 门、变异测试、固定 seed/配置、敏感性扫描、错误撤回机制
已构成足够基础；再加测试对论文说服力的边际收益低于同等工时投入别处。

下一阶段只做两件事，按顺序：

**(A) 外部 Validation —— 独立预测误差实验**（不是"再多几个门"）

```
真实无人机飞行数据（时间 / 速度 / 载荷 / 轨迹 / 电压 / 电流）
        ↓  同工况重放
本项目模型逐条预测（时间 / 能耗 / 航程）
        ↓
独立误差评估：偏差量级、误差分布、误差来源分解、不确定性区间
        ↓
有效范围声明：哪些工况可信、哪些超出模型能力
```

关键约束：**判据必须在比对之前定死并落盘**，否则事后会挑一个好看的口径。
候选源与访问状态见 §5；PX4/Gazebo SITL 只可用于**跨仿真器对照**，不得冒充真实飞行观测。

**(B) 论文贡献层面：把"可信度评估方法"做成可重复的对照实验**

仅汇总开发日志不构成研究贡献。要回答的问题是：

> 这套可信度评估方法，相比没有这些措施的普通仿真工作流，能发现哪些**原本不容易被发现**的问题？

本项目已经攒下四个**真实案例**，每个都有当时的先红后绿证据，可直接作为实验素材：

| 案例 | 缺陷类型 | 无此方法时的表现 |
|---|---|---|

| 优化器未实际介入（轻载 buffer 峰值 2 < 阈值 15） | "四算法对比"其实是同一算法 | 结论看起来完全正常 |

**注意**：这一节记录的是"下一步要做成可重复对照实验"，不是"已经做了"。
