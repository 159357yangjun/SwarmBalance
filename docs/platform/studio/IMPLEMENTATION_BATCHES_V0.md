## 第一序列：统一用户体验与持久对象

### B0 — 需求与交互边界（当前文档交付）
- 从现有控制台梳理所有任务入口、对象、状态和历史结果；出 G0 功能覆盖矩阵、G1 线框/操作矩阵、候选数据契约。
- 确认“统一工作台”与“原控制台兼容路径”的范围：新功能默认 opt-in，旧路径保留。
- 禁止本阶段调整算法/运动/能耗/历史指标。

### B1 — 项目和资源总线
- 统一项目上下文与路由；旧 `/workbench` 可保持入口但不再与 `/map-lab` 形成不关联状态。
- 资源导入管理：地图文件、场景配置、独立模型资源；提供原始格式/来源/许可/摘要和缓存引用。
- `MapPreviewPackage` 和“可计算 World”分开；不能默认把 GIS 预览资源标记为 simulation-ready。
- 验收：项目 A 和 B 的资源与编辑状态互不串扰；保存/关闭/重新打开能恢复引用。不得重写 `console/mvp_service.py` 旧格式，新增适配与版本层。

### B2 — World/Scenario 草稿与修订
- 版本化 World/Scenario，显式空间参考、几何/单位、静态实体、初始状态、规则及事件源。
- 导入/复制/保存新版本、未保存警告、属性校验、失败回滚。
- 先完成二维对象管理和外部数据引用，不做复杂三维编辑器。
- 验收：导入资源 → 创建 World v1 → Scenario v1 → 保存 → 重开 → 版本、对象、事件不变；错误文件不导致半保存状态。

### B3 — 场景工作台的全部日常操作
- 将地图导入、图层管理、机巢/机队/任务/限制管理、规则面板整合到同一工作区。
- 明确编辑工具的状态、选中对象 ID、撤销、错误恢复和保存。
- 验收：无人工修改 JSON 或 Python 命令完成上述操作；验证键盘、不同视口与旧界面退化。
  
## 第二序列：仿真内核与结果框架

### B4 — 规则、事件和时钟引擎
- 先解决 ARCH-06 的 P0 接口冲突、会签和旧基线取证；不得自行宣称发布 v1 ABI。
- 独立 Harness 管理生命周期、仿真时钟、事件排队/验证/提交、状态所有权和资源能力协商。
- “演示级确定性组件”完成事件与位置演示，不声称飞行物理/能耗已经验证。
- 验收：相同脚本/版本重复执行，事件与状态一致；错误/取消/恢复均有明确日志，异常不能静默提交。

### B5 — 统一运行、记录与回放
- UI 的运行区与场景区共用项目上下文和对象检查器。运行不可直接编辑历史 World/Scenario。
- 运行时间线、对象/事件联动、轨迹回放、资源和组件来源记录。
- 验收：Run 开始→暂停→单步→恢复→停止/完成→保存→重新打开→只读回放可见；异常与中断有独立终态。
- 禁止用渲染帧作为计算状态的单一来源。

### B6 — 完整平台 G3 与迁移
- 用户实测完整任务流、错误恢复、数据版本、跨项目隔离、运行证据、旧系统并行。
- 旧 Yangpu/SimSession/legacy_direct 依然可运行，历史 frozen 产物不改变。
- 所有功能明示完整/受限/实验版，保留最小可回退切换。
- “工程上可操作的平台基础版”放行，不宣称物理真实性与科研模型有效性。

## 第三序列：最后才做的专项研究

### B7 — 实际运动/能耗、航路、机巢和调度算法
- 待平台完成后以独立组件/数据版本接入，复用同一 Run/Record/Replay 机制。
- 每个模型标注有效域、输入数据要求、验证来源、单位及误差，不允许将默认值伪装真实值。
- 优化算法和多策略对比保持独立研发路线，不反向绑死平台设计。

## 全批次统一交付合同

每批必须提供：
1. 真实仓库 HEAD/基线，改动文件和未改动边界；
2. 面向用户的完整任务和状态；空态、失败、取消、恢复；
3. 正例/负例运行命令和实际证据；UI 的 G3 需要浏览器走查，不能以静态截图代替；
4. 兼容路径和回退方法；
5. 未完成能力与阻断项；不是所有清单绿色就能称“仿真可信”。

**开发次序可以并行**：B1 资源协议和 B3 控制台视觉组件可平行准备；但 B2 的 World/Scenario 持久契约要先定清才整合，B4 的状态提交 ABI 必须等 ARCH-06 冲突处理完成。
