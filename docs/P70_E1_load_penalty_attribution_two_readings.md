# 阶段⑤（口径入档，不动实现）：分叉段载重惩罚归属的**两种并列口径**

基线 79ce795。上位裁定 (一)：**只入档口径、不改代码**；要求三件 —— ① 两种可选口径并列写、不得选一藏另一；
② 写明哪一行现在按哪种口径在跑（真实行号 + 原文）；③ 声明"未定口径前不得对外声称 Wh/km"并归入对外红线。

## 0. 一句话事实：本仓**现在同时**在跑这两种相反口径

同一个物理段（无人机被派单后、还没取货的那段飞往 source 的空驶）：
- **能耗侧**把它算成"载货" ⇒ 吃 `load_penalty_factor` 惩罚；
- **里程/KPI 侧**把它算成"空载" ⇒ 计入 `empty_load_ratio` 的空驶分子。

⇒ 这不是"待选的设计方案"，而是**已经共存于生产代码里的不一致**。谁被引用数字时都可能踩到。

## 1. 现场原文（真实行号，本轮从 HEAD 现读）

### 口径甲 · 「载荷 = `current_load` 真值」（能耗侧，当前生效）
`frontend/drone.py:170`：
```python
        load_factor = (self.current_load / self.carrying_capacity) * self.battery_load_penalty_factor
        total_consumption = base_consumption * (1 + load_factor) * self._wind_factor(wind_along)
```
写入时机 `frontend/drone.py:247-249 add_load()`，而环境**在派单时刻**就调用它
（这一点由对面那段注释亲口承认，见口径乙）。卸货点 `:244`（回巢）、`:343`（任务完成，属禁改三段之一）。

⇒ 后果量级（一手，`docs/C3_state_field_audit.md §3.3`）：
```
飞往取货段 109497.5 m / 7847.1 Wh 占加载能耗 48.7%
```
即**约一半的"载货能耗"其实花在还没拿到货的空驶段上**。

### 口径乙 · 「载荷 = 航线标签（下一个任务航点是 source 还是 dest）」（KPI 侧，当前生效）
`frontend/environment.py:1741-1758 _is_carrying()`，其 docstring 原文（`:1742-1749`）就是对本问题的答复：
```python
        注意不能直接用 `current_load > 0`：环境在**派单时刻**就调用 add_load，
        因此"飞往取货点"的那一段也会被认为是载货，空载率会被低估到接近 0。
        正确口径是看航线上下一个任务航点：
          * 下一个任务航点是 source → 还没取货 → 空载；
          * 下一个任务航点是 dest   → 已在送货途中 → 载货；
          * 没有任务航点（如飞往机巢 / 空驶调度）→ 空载。
```
消费点唯一：`frontend/environment.py:1168`（累计 `total_flight_distance` / `total_empty_distance`）。
该口径已由常驻门守着：`console/test_c4_is_carrying_discriminator.py`（F1/F2/F3 + 变异面 M1/M2，[G]），
另有扫描门 `console/test_c4_cargo_truth_scan_gate.py` 禁止新代码用 `current_load>0` 当载货真值。

⚠ 关键不对称：**口径乙有常驻门，口径甲没有。** 且扫描门的措辞是"禁止**新代码**拿 current_load 当载货真值"
⇒ `drone.py:170` 这条**既有**用法正是它豁免的那一类（历史代码，不在违规计数里）。
⇒ 也就是说：本仓已正式认定"用 current_load 判载货"是错的（口径乙 docstring + 两把 [G] 门），
   但同一句话在能耗公式里仍然每天在跑，且没有任何门守着它。

## 2. 两种口径各自的适用条件与后果（并列，不选一藏另一）

| | **口径甲：载荷 = `current_load`（能耗侧现状）** | **口径乙：载荷 = 航线标签（KPI 侧现状）** |
|---|---|---|
| 物理主张 | 电池要为"即将承载的重量"预付：起飞前把货算进配平/悬停功率 ⇒ 派单即加惩罚 | 只有真正带货飞的那段才多耗电 ⇒ 没拿到货就不该罚 |
| 现实依据 | 真机上挂载荷后即使空驶也确有多耗（配平/阻力），但**方向对、幅度无实测来源** | 与"货物是否在机上"这一可观察事实严格对齐，且能保住空载率的区分力 |
| 适用条件 | 关心**总电量/换电次数**是否够用（续航可行性、机巢拥堵）——宁可高估消耗偏保守 | 关心**里程归因类 KPI**（空载率、每单实际载货里程）——必须与物理事件对齐 |
| 若统一采用它 | `empty_load_ratio` 会被低估到接近 0（docstring 已实测过这个后果），KPI 失去区分力 | 能耗侧的空驶惩罚消失 ⇒ 总消耗下降 ⇒ 完成率/换电次数上升，**会改变调度结论** |
| 若维持现状（两套并存） | 两处读数**不可相加也不可互相校验**：`Wh/km` 的分母来自口径乙的里程，分子来自口径甲的惩罚 | 同左 |
| 谁守 | **无常驻门**（扫描门只禁新代码） | `test_c4_is_carrying_discriminator` + `test_c4_cargo_truth_scan_gate`（均 [G]） |

⇒ 真正的选择不是"哪个对"，而是：**要么承认能耗模型是"派单即预付"的保守近似并明写它、
要么把 `drone.py:170` 改成按航线标签取惩罚（动能耗语义）**。后者属 scheduler/energy 语义变更，
需单独授权，且要先解决下面第 4 节的系数来源问题，否则只是把一个 assumption 换成另一个。

## 3. ③ 对外红线（本轮新增一条，归入既有清单）

> **红线：在"分叉段载重惩罚归属"口径确定之前，本项目不得对外声称任何 `Wh/km` 绝对值。**
> 理由（可复算）：`Wh/km` 的分子含 48.7% 归属未定的载重惩罚，分母的载货/空驶划分用的是**另一种口径**
> （§1 甲 vs 乙）。两个口径不一致时，商没有定义。

归入位置与既有条目的关系：
- 与 `docs/#65_parameter_provenance.md:78`「机型不同 ⇒ 只能校结构关系，不可拟合或背书任何机型的绝对 Wh/km」
  **并列而非重复**：那条说的是"外部数据不能给绝对值背书"，本条说的是"内部两个口径自相矛盾时商本身无定义"。
  ⇒ 两条**同时**成立，任一条都足以否掉对外声称。
- 与 `docs/C3_state_field_audit.md:101` 是同一条待办的正式化（那里写的是"必须先定口径（另轮）"，本轮就是那"另轮"）。

允许对外说的仍是：能耗函数的**结构关系**（逆风更费电、顺风省电但有下界、载重单调升），
以及"单位为仿真内部相对量、非标定值"。

## 4. 为什么本轮只做入档是对的（不是回避）

`docs/无人机设备数据源与能耗标定方案.md §2` 记录：E1 主锚点 CMU KiltHub 下载页返回 403 ⇒ **文件未取到，属未验**。
⇒ 现在把惩罚挪到口径乙，等于用一个同样无源的假设替换现有无源假设，且会改变调度行为面
（消耗↓ ⇒ 换电↓ ⇒ 完成率可能↑），属于"为让某个数好看而改语义"那一类。
⇒ 顺序应是：**先取到标定数据 → 再定归属口径 → 最后才谈改哪一行**。本轮停在第一步之前的口径登记。
